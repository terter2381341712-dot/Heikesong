本轮重点验证：

- 两种 NOT_PREPARED 都经历自动准备、等待、P2 重启、READY、执行、结果和 ZIP；目录随后变更不覆盖 Job 的冻结目标，准备始终不消耗接受尝试。
- READY 的空/错摘要、verified=false、失败或缺失 calibration、缺失 backend/provider/model_sha256 不派发，也不自行替节点重新准备；正确资源恢复后原 Job 可继续。
- PREPARING、ERROR/UNAVAILABLE、离线、模式、占槽和清理状态均有原因；同一轮多个 Job、重启后仍不重复准备。
- 准备受理前/后 503、GET 404、准备响应关联错误保留原请求；确定拒绝遵守退避，FAILED 不紧密循环，真实 READY 快照或新会话可恢复。
- 原有结果校验、三次已接受尝试、拒绝计数、未知执行、取消竞争、恢复阶段和单个结果暂不可取回的回归通过。进程测试仍使用显式模拟 P1，覆盖 P2 真实 TCP 启停、重启和 P1 停止后的离线结果/ZIP。

[MOCK 冷节点持久化证据](p2-plan-mock-evidence.json) 从本次测试完成后的 P2 临时数据库只读导出，包含两个场景的创建请求、准备请求/最终状态、执行请求、最终 Job 和 OCRResult；导出时再次按原 schema 验证并比对结果 SHA。它是最终快照而非逐事件日志，准备期间无尝试、原 ID 重放等中间行为由对应测试断言及 JUnit 记录证明。没有将模拟节点、后端或文字标成真实证据。

## 接口一致性结论

原始 `D题参赛执行包/contracts/openapi.yaml` 与 `P2/contracts/openapi.yaml` 逐字节一致，SHA-256 仍为：

```text
376f565d7077ae5de41a0270c1c8c6c1952dc1526b0bc4219ee2f6b8b5b93a31
```

公共路由、字段、必填、状态枚举、HTTP 返回码和版本未变；只实施计划明确的状态选择及等待语义。P2 的 HTTP API、P1Client、schema 校验器、数据库结构、输入拆分与结果汇总代码均未改动。原样例副本和新增共享 Capability 副本也分别与来源一致，来源/hash 见 [契约记录](../contracts/README.md)。

- PreparationRequest 仍为六字段，使用 Job 的非空目标与所选节点当前会话；接纳未知不能根据超时、5xx、单次 GET 404 换 ID。
- ExecutionRequest 仍使用原十二字段、Job 参数、输入 ID、当前 worker/session 与目录规定的 timeout_seconds；准备/拒绝不计 attempts_used，最多三次已接受尝试。
- P2 返回 Job/Task/JobResults/错误均继续按原 schema 校验；下载前严格校验结果字节长度、SHA、OCR schema、类型/输入关联、尺寸与坐标。成功结果持久化后才报告成功；下载暂不可用不重新推理。
- P2 能检查 READY 声明是否完整一致，但不能凭资源响应证明实际权重、环境和自测真实性；这些由 P1 核验并在真实联调中证明。
