# 第三阶段：按实测耗时调度 CPU / GPU

P2 在现有剩余槽位机制上，选择预计更早完成任务的空闲节点。实现集中在 `task_service/scheduling.py`、`service.py` 和 `store.py`。P1 的原子接纳、CPU 多槽、GPU 单槽、模型常驻、取消和停止确认流程保持不变；公开接口仍为 **0.3.0**。

## 选择过程

1. 先检查节点在线、ACTIVE、无清理屏障、资源快照一致、profile/digest 匹配、能力 READY、模型 SHA 与自测齐全。CPU 必须对应 CPUExecutionProvider，CUDA 必须对应 CUDAExecutionProvider；CUDA 节点只允许一槽，声明的 CPU 多槽预算必须有效。
2. 容量继续使用 `min(available_slots, max_slots-reserved_slots)`，再扣除尚未出现在快照中的待对账请求。同轮派发立即扣减；没有空槽的节点不进入排序。不会把任务排在忙 GPU 后面，同时让可用 CPU 空等。
3. 对每个可用节点估计本图片的执行耗时。已准备节点优先执行；没有可执行槽时才为匹配的冷节点发起准备。持续只有小 Job 时，每到探索轮次还会在派发后预热一个冷节点，避免新加入的 GPU 永远没有自测机会。探测到 GPU 只影响预热次序，不构成执行资格。
4. 正常轮次按预计耗时排序，同分继续使用节点轮转。每第 8 次持久派发、且有两个以上候选时，选择当前图片规模下样本较少、最近观测较旧的可用节点，补充实测数据。探索不会绕过资格或容量检查。

**没有“GPU 固定快 N 倍”的乘数，也不按 GPU 计算核心数分槽。** 小图、慢传输、显卡驱动或 CPU 预处理都可能使 GPU 总耗时更长，实测较快的 CPU 可以优先。

## 估计与历史

历史按以下身份隔离：worker、task_type/profile_id/digest、任务参数、backend/provider/model SHA、max_slots/threads_per_slot/cpu_thread_budget，以及稳定硬件信息。普通会话重建可以复用同配置历史；更换后端、模型、线程或槽数会形成新身份。

图片按像素分四桶：≤25 万、≤100 万、≤400 万、>400 万像素。默认读取同身份、同桶、最近一小时内最新 32 条成功样本。

- 样本包含真实 inference_ms、download_ms 和 total_worker_ms 剩余开销。桶内按像素比例的平方根修正推理耗时（限制为 0.5–2 倍），按文件字节比修正下载耗时（限制为 0.25–4 倍），使用 α=0.3 的指数加权平均，近期观测权重更高。
- 评分为 `预计耗时 × (1 + 0.25 × 已占用/不可用槽比例)`，对同一 CPU 池的并发争用作轻度保守修正。这是启发式评分，不是完成时限保证。
- 没有同桶有效历史时，回退到 P1 当前会话已通过自测的 median_compute_ms，按图片像素作保守缩放，并加上 10 MiB/s + 5 ms 的下载先验。参考像素为约 15 万。这些是明确的启动假设，不是真实带宽或 GPU 性能证据。
- 失败、取消、无效结果、丢失或不一致的耗时、零推理耗时、非有限数、超出执行期限的观测不进入历史。普通 Job 已请求取消也不采样。派发已超过历史有效期才收到的迟到结果仍可正常收敛，但不被当作新鲜性能样本。
- 采样与结果成功状态在同一 SQLite 事务提交，execution_id 唯一，重启和重复对账不会重复学习。没有第三阶段派发元数据的历史任务仍可完成，但不会被错误归入某个后端。

OCR 文本密度、长宽比、模型内部缩放和共享机器的其他负载仍会影响耗时；像素桶只能粗略估计。CPU/GPU 利用率与内存遥测保留作观测，不直接变成准入阈值。本阶段没有动态内存/显存配额、跨 Job 优先级、抢占或新的公平调度。

## I/O 与安全语义

独立执行和准备请求的对账、结果下载使用有上限的并发。每个对账/下载步骤有单独超时，原 execution_id 和准备 ID 保留，不能把网络不确定性当成失败后另建执行。某节点对账不确定时暂不向其派新任务，其他健康节点仍可以接单；有健康节点时不会因另一节点故障对整轮采用指数退避。

结果暂时取不回的成功执行不占计算槽。单个慢请求仍会受到本轮有界等待，多批请求的最坏等待受并发数和超时影响；这不是完全无阻塞的分布式调度器。新派发继续逐项持久化后对账，批量 POST 并发尚未引入。

Job 取消仍停止新派发，并等待原执行确认；关闭共享的 NODE_UNAVAILABLE 重试标记仍按原规则迁移；已成功结果不重算。后台循环取消/退出会取消并等待所有对账协程，避免关闭数据库后还有后台写入。

## 配置与数据

默认直接启用，无需调整 P1 节点启动参数。

| P2 环境变量 | 默认值 | 用途 |
|---|---:|---|
| TASK_SCHEDULER_CONCURRENCY | 8 | 对账/结果 I/O 最大并发，1–64 |
| TASK_SCHEDULER_IO_TIMEOUT_SECONDS | 5 | 单次对账或下载步骤的超时秒数，必须为有限正数；慢网络可调大 |
| TASK_SCHEDULER_HISTORY_TTL_SECONDS | 3600 | 历史样本有效期，有限正数 |
| TASK_SCHEDULER_EXPLORATION_INTERVAL | 8 | 每多少次派发探索一次，至少 2 |

P2 启动时自动新增两张表，旧 Job 数据保留：

- `scheduling_decisions`：每次派发的后端、图片规模、估计来源、样本数、评分、剩余槽、探索标记及其他候选评分；与原执行请求同时提交，先于网络 POST。
- `scheduling_samples`：每个已验证成功执行一条真实耗时观测，按资源身份/像素桶/时间建立索引。

两表是内部诊断数据，不加入 Job 公共 JSON 或导出 ZIP，不包含服务令牌、OCR 文本和输入文件内容。当前与 Job 历史一样保留记录，没有自动清理旧记录；TTL 和 32 条上限限制的是估计读取窗口。

可只读查看最近决策（将路径替换为实际 TASK_DATA_DIR）：

```sh
sqlite3 /绝对路径/TASK_DATA_DIR/tasks.sqlite3 \
  'SELECT execution_id,decision FROM scheduling_decisions ORDER BY sequence DESC LIMIT 10;'
```
