# P2 → P1 真实联调清单

本清单适用契约 0.2.0。P2 已实现 OCR Job 管理和调度；P1 承担资源服务、文件机制、模型准备及单图 RapidOCR / ONNXRuntime 执行。模拟测试通过不代表下列真实能力已交付。

本轮按 [统一计划 1.0](../../P1-P2统一修改与联调计划.md) 核对，P2 的修改与测试见 [实施报告](P2-统一计划实施报告.md)。本文说明双方公开接口的交接要求，不包含 P1 实现改动；P1 修改由队友按计划第 4 节处理。

## 1. 接口清单

所有 P1 路径使用 `/api/resource/v1` 前缀；P2 通过 HTTP 调用，不读取 P1 数据库、节点端口或本地路径。

| 接口 | P2 用途 | P1 必须保证 |
|---|---|---|
| GET /healthz | 人工/自动联调前检查 | service=p1_resource、contract_version=0.2.0；不以健康检查替代模型就绪 |
| GET /task-types | 校验类型、语言、输入限制与冻结 profile | CONFIGURED 才有真实 digest；OCR result_schema=OCRResult；未配置原因明确 |
| GET /resources | 选择节点及空槽 | ONLINE、ACTIVE、session、cleanup_pending、空槽、逐 profile 能力真实；READY 对应自测通过 |
| GET /artifacts/{id} | 创建 Job 前读取输入元信息 | 原字节 SHA、真实 MIME、大小、EXIF 纠正后的宽高、相对 download_path；ID 与请求一致 |
| GET /artifacts/{id}/content | 下载结果 JSON | 成功执行引用的文件已经持久化，长度和 SHA 与 Artifact 一致 |
| POST /preparations | 空闲兼容节点准备 OCR profile | 请求 ID 幂等；同 ID 不换载荷；准备与执行共用单槽；快速返回受理状态 |
| GET /preparations/{id} | 准备对账与进度查询 | ACCEPTED/DOWNLOADING/LOADING/VERIFYING/READY/FAILED/REJECTED；失败理由明确 |
| POST /executions | 指定节点执行一张图片 | 原子校验会话、profile 和槽位；201 接受；同请求重放 200；业务拒绝 409 并持久记录 |
| GET /executions/{id} | 接纳对账、状态查询、读取结果引用 | 原请求、输入 SHA、接纳时间、终态、结果 artifact 和错误信息完整；成功可下载 |
| POST /executions/{id}/cancel | 取消 Job 的活动执行 | 活动执行可返回 202 CANCEL_REQUESTED；实际确认后终态；成功与取消竞争由 P1 决定 |
| POST /artifacts | **P3/P4** 上传真实联调图片，P2 当前不调用上传 | multipart upload_id + file；保存原字节，返回可被 P2 查询的 INPUT Artifact；上传幂等 |

P2 本轮不依赖 P1 events 或节点模式修改接口，也不直接注册 Worker。所有响应（含错误）须符合仓库的原始 OpenAPI，而不是框架默认错误格式。

## 2. 配置交接

| 配置/材料 | 提供或确认方 | 要求 |
|---|---|---|
| RESOURCE_BASE_URL | P1 | P2 机器实际可达；仅协议、主机、端口；无路径或尾斜杠，跨机不能填写 localhost |
| TASK_TOKEN | P1/P2 | 允许 P2 查询、准备、执行及取消；只在服务端；与 DEMO_TOKEN 不同 |
| DEMO_TOKEN | P1/P2/P3/P4 | 两服务演示令牌一致；前端通过 Authorization: Bearer 发送 |
| RESOURCE_BIND_HOST / RESOURCE_PORT | P1 | 约定 0.0.0.0 / 8001，核对局域网防火墙及可达性 |
| RESOURCE_DATA_DIR | P1 | 独立绝对目录；不得与 TASK_DATA_DIR 共用数据库或数据文件 |
| TASK_BASE_URL | P2 → P3/P4 | P2 默认 8002，前缀 /api/task/v1；独立配置前端代理 |
| TASK_DATA_DIR | P2 | 持久目录，重启沿用；单个 P2 worker 独占；不得用测试目录替换正式数据 |
| profile.lock.json 及其原字节 SHA-256 | P1 | digest 不是占位字符串，锁文件内不包含自身 digest；提供许可证与权重来源记录 |
| 节点与会话清单 | P1 | worker_id、session_id、设备信息、backend/provider、自测、可用槽位；未知硬件字段为 null |

P2 不需要 JOIN_TOKEN 或节点会话凭证。没有 P1 配置时，P2 健康检查仍可工作，创建新 Job / 查询类型返回依赖不可用；已有 Job、持久结果和终态 ZIP 仍可读取。

## 3. OCR profile 内容

- task_type=`ocr.image.v1`，首个 profile_id=`ocr.default.v1`，result_schema=`OCRResult`。
- 首版输入 JPG/PNG，单图不超过 10 MiB、20,000,000 像素，一文件一个 Task；语言 `auto/zh/en` 以 P1 实测发布为准。
- 计划基线：RapidOCR 3.7.0 + ONNXRuntime 1.23.2，PP-OCRv4 轻量检测/识别及对应方向分类 ONNX 模型，FP32。**P2 未安装或验证这些模型**；实际发布版本及依赖由 P1 自测并锁定。
- 锁定检测、分类、识别模型及字典的来源、许可、SHA；记录完整依赖、预处理、缩放、阈值、文字排序、批大小和各设备线程预设。
- 两台 Mac 先验证 CPUExecutionProvider；Windows 先 CPU。CUDA 必须验证后端和结果质量后登记，不能静默回退并假报 GPU；不新增 backend 枚举。
- 每节点一槽，模型准备也占槽。模型常驻复用；P1 负责实际内存门槛、加载、自测、取消清理与工作进程终止。
- OCR bbox 是纠正 EXIF 后的原图坐标；图片缩放须映回。四点框转轴对齐矩形；文字块和全文排序固定。空识别允许空 text/blocks，但质量由 P4 另判。
- P1 可将首个真实 OCRResult、对应输入 artifact 和完整 Execution 交给 P2，作为最小联调样本；不能提交模拟样例冒充真实识别。

## 4. 不能省略的协议语义

准备和执行选择遵循计划第 3.4–3.5 节：

- ONLINE/ACTIVE、无清理、无活动准备或执行、reserved_slots=0 且 available_slots=1，才有新准备/执行的候选资格；模型未准备不阻止空槽可用。
- 先按 task_type/profile_id 找能力。NOT_PREPARED/verified=false 时，null 或匹配摘要均可准备，发出的非空 digest 取自 Job；不同摘要等待配置对齐，不修改 Job。
- PREPARING 查询已存 preparation 或等待快照，不新建第二个准备；ERROR/UNAVAILABLE 展示原因，不紧密自动重试。
- READY 要求 digest 严格相等、verified=true、calibration.passed=true 及非空 backend/runtime_provider/model_sha256。P2 检查这些公开证据，不替 P1 检查权重；缓存标志不能代替 READY。
- 原始样例及新增完整 Capability 对象统一见 [共享样例与联调入口](../../qa/p1-p2/README.md)。其中 MOCK 值不得用于真实 profile 或验收证据。

1. Execution 请求包含 execution_id、job_id、task_id、attempt_no、worker_id、worker_session_id、task_type、profile_id、profile_digest、input_artifact_id、parameters、timeout_seconds。P2 发出前持久化全部字段。
2. 同 ID 同载荷始终返回原记录；同 ID 不同载荷 409。REJECTED 必须可 GET，且原 ID 永远不会后来变成 ACCEPTED。
3. P2 的 HTTP 超时不是执行失败。GET 404 后只重放同 ID；P1 故障时 P2 保留请求等待对账。不要要求 P2 因一次 404 换节点或换 ID。
4. P2 默认执行期限取类型目录值（OCR 初值 120 秒）。P1 管硬期限、租约、节点失联和明确终态。P2 最多三次已接受尝试，拒绝与准备不消耗预算。
5. 非重试错误（输入、输出、profile 不匹配）结束该 Task。可重试 FAILED 才进入新尝试，P1 不另做跨节点重派。
6. 成功结果先持久化再发布引用。结果传输故障只重取原结果。P1 先成功的结果在取消竞争中保留；取消先撤权则不收迟到提交。
7. P1 重启后保留幂等及终态记录；旧活动执行明确 FAILED/RESOURCE_SERVICE_RESTARTED，新会话不能接纳旧结果。
8. 错误使用声明的 code/retryable/details。不要在 message、文件名、结果或错误细节中放令牌、服务器路径或参考答案。
9. PreparationRequest 只包含 preparation_id、worker_id、worker_session_id、task_type、profile_id、profile_digest。准备的 503 也表示接纳结果待查；先 GET 原 ID，404 时同 ID/载荷重放。已拒 ID 保留拒绝记录；P2 仅在确认 retryable 的 REJECTED 且退避至少 1 秒后换 ID。失败原因通过等待状态展示。

## 5. 接入顺序与交接证据

先确认双方版本/鉴权与文件元信息，再让一台兼容真实节点以 NOT_PREPARED/null 上线，通过 P2 创建一张新图片的 Job。由 P2 自动请求准备；验收客户端不能先手工 POST preparation。核对 Job → preparation → READY → Task → execution → worker/session → 输入 SHA → 结果 SHA；确认准备期间 attempts_used=0，最终单输入成功的接受尝试为 1，P2 结果及 ZIP 关联一致。

然后按统一计划 L01–L19 扩大为多图片、两台物理设备，验证等待准备、忙碌拒绝、响应丢失、失败重试、取消、P1 中断恢复和 P2 重启。X01（P1 重启）由 P1 主责，X02（P2 重启）由 P2 主责，另一方配合对账；本轮由 P2 汇总联调记录，P4 参与时独立复验。最后另行进行参考文本质量核验及同口径性能测量。

当前仍待 P1 提供：真实地址及令牌、模型锁文件、已自测节点、文件上传/下载、真实 OCR 结果和故障语义验证。模拟 P1 的两个节点、预置 PNG 和固定文字均不能作为这些交付的替代品。
