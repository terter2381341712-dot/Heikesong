# 一体化打包方案（方案稿，未实施）

> 目标：双击一个应用即可用，不出现命令行，不需要用户理解 Python/Node/conda。
> 前提：消除「这台能启动那台不能」的平台差异。
> 状态：仅方案，无代码改动。

## 1. 现状链路

```
Windows: P4\start.cmd  ─┐
macOS:   P4/start.command ─┴→ bootstrap.ps1 / bootstrap.sh
                              ├─ 下载 micromamba（GitHub，SHA256 校验）
                              ├─ 建 bootstrap 环境 python=3.12.15（conda-forge）
                              └─ exec managed_runtime.py
                                   ├─ ensure("web")  → nodejs=22（conda-forge）
                                   ├─ ensure("P1")   → python=3.12.15 + pip install -r P1/requirements.lock.txt
                                   ├─ ensure("P2")   → python=3.12.15 + pip install <pyproject 里的依赖>
                                   └─ ensure("CUDA") → 仅 Windows，额外 cuda-version/cudnn
                                        ↓
                                     control.py（8003）→ 启动 P1(8001)/P2(8002)/web(5173)
```

每次启动都会重新执行 `Manager.ready()`：导入真实模块、逐条核对版本号。任一环节不通过就重新安装。

## 2. 为什么 Windows 和 Mac 会交替失败

不是跨平台代码不兼容，而是**每次现场解析依赖 + 每次现场联网**。按影响排序：

| # | 成因 | 平台 | 证据 |
|---|---|---|---|
| 1 | **macOS 的 bootstrap 锁是目录，进程被强杀后不释放** | macOS 独有 | `bootstrap.sh:14` 用 `mkdir` 加锁，只有正常退出才 `rmdir`；提示文案直接写「若上次意外退出，请…删除 .bootstrap-lock」。Windows 用 `[IO.File]::Open(...,'None')`，进程死亡自动释放。**这是「Mac 突然不能启动」最常见的原因，且只能手工恢复** |
| 2 | **P2 的 `uv.lock` 在运行时被绕过** | 两端 | `managed_runtime.py:requirements()` 从 `pyproject.toml` 正则抠依赖列表再 `pip install`，完全没读 `P2/uv.lock`。锁文件只在开发者手工 `uv sync --frozen` 时生效 |
| 3 | **P1 依赖大面积浮动**（已修） | 两端 | 原先 `P1/requirements.txt` 10 个包只有 3 个用 `==`。现已生成 `P1/requirements.lock.txt` / `requirements-gpu.lock.txt` 全量固定版本，启动器只装 lock 文件 |
| 4 | **全链路无国内镜像** | 两端（国内网络） | micromamba 走 GitHub Releases，conda-forge 走 anaconda.org，pip 走 PyPI。三个源在国内都不稳定，超时/半途失败表现为「这次不行，重开又行」 |
| 5 | **`bootstrap.sh` / `bootstrap.ps1` 没有 eol 规则** | Windows 检出 | `.gitattributes` 只钉了 `P4/*.command` 和 `P4/start.cmd`。`core.autocrlf=true` 的 Windows 检出会把 `.sh` 转成 CRLF，bash 直接报 `bad interpreter` |
| 6 | **运行环境放在仓库内 `P4/var/runtime`，且 `var/` 被 gitignore** | 两端 | 每个 worktree / 每次换目录都要从零下载数百 MB；换分支或移动目录后环境失效，表现为「昨天好好的今天不行」 |
| 7 | **端口写死 8001/8002/8003/5173** | 两端 | 上次异常退出留下的进程占端口，本次启动直接失败，需手工结束进程 |
| 8 | **CUDA 只有 Windows 路径** | Windows | macOS 上 `ensure("CUDA")` 直接抛错（正确），但两条分支不同，Windows 多了 cuda-version/cudnn 的解析，是最脆弱的一环 |

已修复的历史问题（不用再管）：P1-WIN-001 模型排序、P4 节点入口在嵌入式 Python 下导入失败、P4 Mac 虚拟环境路径 resolve。
仍开放：P2-WinError32 临时目录清理失败。

另外：Python **3.9 已于 2025-10 结束支持**。已于 2026-11-15 统一到 **3.12.15**，cp312 轮子覆盖四个平台（已核 PyPI）。

## 3. 方案

### 3.1 推荐：构建期打包 + 薄启动器（两层）

**第一层：把「解析依赖」搬到构建机，用户机器只解压。**

- CI（或本地构建脚本）按四个平台各产出一份预装运行包：`win-64`、`osx-arm64`、`osx-64`、`linux-64`，Windows 额外产一份 CUDA 变体。
- 每份包含已装好的 `web/`（Node 22）、`P1/`、`P2/` 环境，用 `conda-pack` 或直接 tar 整个 prefix。
- 产物带 SHA256 清单；用户端**只校验 + 解压**，不跑 conda、不跑 pip、不联网装包。
- 首次运行仍需下载（或随安装包附带）。下载源换成国内对象存储（阿里云 OSS / 腾讯云 COS），支持断点续传和 SHA 校验；GitHub 只作为回退源。
- 体积估算：P1 环境（onnxruntime 11–17MB + opencv 44MB + numpy 14MB + 其余）约 180–250MB/平台，压缩后约 80–120MB。

**第二层：把 `start.cmd` / `start.command` 换成一个 GUI 启动器。**

- 技术选型：Electron 或 Tauri 外壳（只需一个窗口 + 进度条 + 按钮，不需要渲染复杂界面，内嵌现有 `http://127.0.0.1:5173` 即可）。
- 界面只有三态：`准备中（进度条）` → `已就绪（启动中心 / 加入算力池 两个按钮）` → `出错（一键复制诊断信息 + 打开日志）`。
- 启动器负责：解压/校验 runtime、拉起 `control.py`、等待 5173 健康检查、打开内嵌窗口、退出时清理子进程。
- 用户全程看不到终端。

**关键收益**：依赖解析从「每次运行」变成「每次发版」。Windows/Mac 跑的是同一份构建产物，平台差异被钉死在构建时。

### 3.2 备选：单文件可执行（不推荐）

PyInstaller / Nuitka 把 P1+P2+control 打成一个 exe/app。问题：

- onnxruntime 的 DLL 加载、opencv 的隐藏依赖在 PyInstaller 下需要大量 hook；
- macOS 需要 codesign + notarize，否则双击被 Gatekeeper 拦；
- CPU 与 CUDA 必须分两个包，且 CUDA 版还要绑 CUDA/cuDNN；
- 每次改代码都要重新打包验证。

工作量与风险都明显高于 3.1，收益只是「一个文件」。

### 3.3 不适用：容器

Docker Desktop 本身需要用户安装、要命令行、要配镜像源，与「不想见到命令行」直接冲突。

## 4. 无论选哪个方案都该先做的修复

这些能立刻消掉大部分「偶发不能启动」，且与打包方案解耦：

1. **macOS 锁改成 flock**（最高优先级）。把 `bootstrap.sh` 的 `mkdir` 锁换成 `flock` 文件锁，进程死亡自动释放；顺带删除提示里的「请手工删除 .bootstrap-lock」。这一条直接消掉最常见的 Mac 启动失败。
2. ~~P2 运行时改用锁文件~~（已完成）：`managed_runtime.requirements("P2")` 改读 `P2/requirements.lock.txt`（由 `uv export --frozen --no-dev` 生成）。
3. ~~给 P1 补完整 pin 文件~~（已完成）：`uv pip compile P1/requirements.txt --universal --python-version 3.12 -o P1/requirements.lock.txt`。
4. **加镜像与自动回退**。conda 侧配置 `custom_channels` 或直接用国内 conda 镜像；pip 侧 `--index-url` 首选国内源，超时后回退官方。写进 `installers.tsv` 同级配置，不硬编码在代码里。
5. **补 `.gitattributes`**：`P4/scripts/*.sh text eol=lf`、`P4/scripts/*.ps1 text eol=crlf`。
6. **运行环境移出仓库**。放到 `%LOCALAPPDATA%\EdgeFabric\runtime` 和 `~/Library/Application Support/EdgeFabric/runtime`，多份检出共享一份，换分支不受影响。
7. **端口占用自愈**。启动前探测 8001/8002/8003/5173，被占用时先尝试识别并结束本项目遗留进程，识别不出才提示换端口。
8. **一键诊断**。启动器出错时生成单个报告文件（系统架构、各解释器路径与版本、哪一项核验失败、`setup.log` 末 200 行），用户直接发给你。

## 5. 建议的实施顺序

| 阶段 | 内容 | 产出 | 风险 |
|---|---|---|---|
| P0 | 第 4 节第 1、5、6 条 | 现有启动器稳定，Mac 不再需要手工删锁 | 低，改动集中在一个脚本 |
| P1 | 第 4 节第 2、3 条 | 依赖可复现，两台机器装出同样的环境 | 低，只影响装包来源 |
| P2 | 构建脚本产四平台 runtime 包 | 可离线分发的运行包 | 中，需要一台 Windows 构建机验证 |
| P3 | GUI 启动器外壳 | 双击即用，无终端 | 中，Electron/Tauri 打包与签名 |
| P4 | 国内 CDN + 断点续传 | 首次安装体验 | 低，运维为主 |

## 6. 需要你决定的事

1. **是否接受「首次仍需联网下载 80–120MB」**？如果要完全离线，安装包会变成 300MB+，需要提前分发。
2. **GUI 外壳选 Electron 还是 Tauri**？Electron 体积大（~120MB）但生态成熟、签名简单；Tauri 体积小（~10MB）但要装 Rust 工具链、Windows 需要 WebView2。
3. **Python 版本**：已于 2026-11-15 统一到 3.12.15（onnxruntime 1.19.2 支持的最高版本），profile 锁文件与 digest 已同步更新。
4. **构建机在哪**？四平台产物最好在 CI 上做（GitHub Actions 有 Windows/macOS runner），否则要手工在两台机器上各跑一次。
