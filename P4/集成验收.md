# zyc 集成与两人双机验收

开发保持在 `zyc`，稳定 main 不动。冻结输入为 main `0dd6ca50b54a03a1cc11c7f7e8fc3f415404a843` 和 zyc `8690c3cd3e595a0a38ca14cb9fd1bdeca5b9c0fe`。备份标签为 `backup/zyc-before-integration-20261115-012451`。lt、lyj 的冻结远程提交已包含在 main 中，无需再各合一次。

本轮接受用户说明的 main 历史双机验收作为历史基线，同时复跑本机自动检查和真实 OCR。历史验收不等于新版本双机通过。新版本由两位队友各操作一台电脑，其中一台 Windows NVIDIA；不要求提供远程账号。人工图片参考尚未冻结、Windows/CUDA 实测和双机浏览器记录尚未提交时，正式阶段保持 NOT_RUN。代码准备与本机回归结果单列，不建立阶段 PASS 标签、不发布到日常实例。

## 启动方式与计算配置

仍用 `P4/start.command` 或 `P4/start.cmd` 打开工作台，再使用原中心启动、连接码、共享开关。新增配置没有工作台设置页。默认读取 `P4/var/compute.json`，缺少文件等价于 `{}`：default profile、CPU、1 槽、threads=0、轮转调度、关闭预取。模型常驻属于基础执行方式。文件内容错误会拒绝启动，不静默使用默认值。

两种入口共用 `scripts/compute_config.py`；显式路径示例（从项目根目录）：

```sh
python P4/scripts/control.py --compute-config P4/config/compute.cpu-default.example.json
python P4/scripts/cluster.py run --machine P4/var/machine.json --compute-config P4/config/compute.cpu-heterogeneous.example.json
```

`python` 是安装了 `P4/requirements.txt` 的工具解释器；计算环境由启动器独立选择。CPU 模型仍用 Python 3.9.6 与 `P1/requirements.txt`。中心资源服务使用原 CPU 环境；Windows CUDA 节点单独使用 Python 3.11.9 的 `P1/.venv-gpu`，安装 `P1/requirements-gpu.txt`，不得在这个环境再装 CPU ORT。具体 CUDA/模型诊断命令见 [GPU 环境说明](../P1/docs/GPU与常驻模型启动.md)。启动器核验 Python 和锁定的模型依赖，运行准备还要核验 CUDA provider，失败不能转 CPU。

`config/compute.*.example.json` 包含各阶段样例。CPU 多槽需显式 slots/threads/cpu_budget；预算不超过本机核心数。单槽预取另外计一个 CPU 线程预算。GPU 多路样例中的 `gpu_lane_vram_bytes: null` **故意不能启动**：先在实机运行 `node_agent.gpu_probe`，填入实测 `lane_vram_estimate_bytes`，不能把示例猜测值当显存证据。N=1/2/4 各保存独立配置；所有多槽都保持 prefetch=0。

相对 `node.python` 路径以配置文件目录解析。样例保存在 config 下或复制到同层 var 下时相对路径相同；移动到别处需相应修改。配置只在启动时读取。中心和全部节点同时选 default 或 heterogeneous，确认相同 profile 摘要；冻结 lock 文件不修改。配对格式、JOIN/TASK/DEMO 边界保持原实现，计算配置不能包含 Token。升级后代码指纹变化时，沿用已有身份文件和中心 Token，通过原连接码流程重新建立连接；不要删除身份或重新生成整套 Token。

## 两位队友的操作分工

队友 A：中心与 CPU 节点、工作台和验收工具。队友 B：独立 Windows NVIDIA 电脑，工作台与节点。两端使用同一冻结源码和契约 0.4.0，不混用旧节点。每轮记录操作人代号、PC-A/PC-B、系统、解释器、依赖、驱动、配置、profile 摘要和时间。记录中遮盖 Token 和配对码。

1. A 用隔离测试数据启动中心、本机节点；B 按原发现/连接码流程加入。B 不启动本地 P2。复用原配置重启确认 worker_id 稳定，错误连接码应被拒绝；确认节点配对文件只带 JOIN 凭证。
2. A、B 分别在真实浏览器打开工作台，使用 PNG/JPG 上传、提交相同测试集，检查进度和 OCR 预览。保存 Job/Execution、截图、原图 SHA、ZIP manifest 和结果顺序；同一 Job 必须有两个物理设备的成功结果。
3. 对错误/缺失 Token、越权调用、两端代理路由逐一记录。不要把 B 能打开页面当成 B 能通过中心代理提交任务。
4. 分别在空闲、运行时关闭共享，等服务端确认，尝试远程切换模式不能绕过关闭状态；恢复共享、取消 Job、断开 B 网络触发迁移。确认成功结果不丢、有效结果不重复、旧执行未停止前不释放槽位。
5. 断开工作台后恢复，重启节点/P1/P2，重放同请求及冲突请求；确认身份、历史结果、幂等与容量对账。完成启动失败/端口占用提示和 Windows 路径检查；只停止本轮启动的实例。
6. 检查 MOCK、中英文、令牌复制（截图打码）、设备状态、日志、自选图与下载。MOCK 和 HTTP 脚本均不能代替第 2 步浏览器实测。

## 固定阶段门槛

每阶段先跑默认配置的 G0–G7，再跑阶段配置及此前已启用能力。S2 后同时维护 default 与 heterogeneous 两套记录。失败停在该阶段修复。以下每行都还需要完整 G0–G7，不能只凭新增功能脚本放行。

| 阶段 | 额外必需证据 |
|---|---|
| S0 | main 历史验收来源、本机复现、至少 20 张人工核对图片与冻结阈值、同样本三轮基准 |
| S1 | CPU 单槽、轮转、prefetch=0；连续任务只加载一次模型；停止/取消/关闭共享无孤儿进程 |
| S2 | 真实 CUDA provider；CPU/GPU 同 Job；错误 Python/CUDA/profile 明确拒绝；取消回收 |
| S3 | 双槽及设备允许更多槽的真实重叠；预算/派发上限；单槽取消隔离；代次与旧结果隔离 |
| S4 | 无历史时校准；重启保留样本；离线/未就绪/未对账拒绝接单；新节点探索不饥饿；决策日志 |
| S5 | 单槽真实预取命中；取消/迁移/TTL/session/profile 失效；无重复结果、预算未超 |
| S6 | Windows CUDA N=1/2/4 及超显存拒绝；取消、共享关闭、子进程崩溃、晚到结果；实际停止证明 |
| S7 | main 数据副本迁移两次及重启；旧结果可读；回滚代码+环境+数据恢复原 main；全部组合复验 |

GPU 逻辑多路当前共享一份引擎并持有推理锁，推理仍串行，不能宣称 N 路等于 N 倍吞吐。取消一路须收到线程 done 才释放；10 秒仍未结束会终止共享子进程、使所有路重新准备，其他路会被中断。该行为的实际显存回收仍需 CUDA 实测。

自动汇总命令：

```sh
python P4/scripts/check_integration.py --stage S1 --out qa/integration/S1-default-RUNID --real-http
```

可用 `--p1-python`、`--p2-python`、`--p4-python` 指定测试解释器。真实 HTTP 脚本使用项目 P1/P2 的现有虚拟环境和独立 `P4/var/integration/` 数据。汇总脚本不会操作日常服务。退出码 0=完整 PASS、1=FAIL、2=NOT_RUN。没有人工记录时，仅 G0 可以自动 PASS；其他门槛保持 NOT_RUN。

人工文件参见 `config/integration-attestation.example.json`。从报告复制 stage/source_digest/解析后的 compute；将 G1–G7 和累计阶段检查对应文件放在人工文件同目录或子目录，记录 SHA256、operator_attested 与结果。至少两位操作人和两台设备。`--attestation` 校验文件摘要与源码、配置，不代替人工判断内容真实性。优化配置报告还需 `--default-report` 指向同阶段、同源码、默认配置完整 PASS 报告。报告目录必须新建，不能覆盖旧记录。阶段检查可以引用本阶段报告附带的各能力回归文件；其源码和配置须与对应实验一致。

已存在的本机专项脚本可复用，分别为 `qa/p1-p2/check_resident_cancel.py`、`check_sharing.py`、`check_multislot.py`、`check_resource_scheduling.py`、`check_input_prefetch.py`。它们使用本机进程模拟多个节点，结果必须标明 physical_machines=1；不得写成双机或 GPU 通过。

## 图片与吞吐量

先生成候选样本：

```sh
P1/.venv/bin/python P4/scripts/prepare_samples.py --out P4/var/acceptance-candidates
```

Windows 使用 `P1\.venv\Scripts\python.exe`。生成 24 张合成 PNG/JPG 及候选参考，包含旋转、空文本；这不是已验收的数据集。两位队友补充中文、真实困难图，逐图核对文字、来源和 SHA，设定 max_cer 后冻结 references.json。先在冻结 main 上验证质量，再沿用同一图片、参考和阈值。不能为优化版本放宽。没有人工冻结时工具仍可测完成速率，但正确吞吐量为空、报告 MEASURED_NOT_ACCEPTED。

每种配置按 CPU 单机、GPU 单机、双机池三组测量。单机组通过原工作台关闭另一设备共享并等确认；双机组恢复共享。使用同一输入、模型、线程预算和设备，记录温度/后台负载。默认与异构 profile 分开比较；CPU/GPU/池对比应全部用 heterogeneous，不能混用 digest。

```sh
python P4/scripts/throughput.py measure --group cpu --config P4/var/control/center.json --inputs P4/var/acceptance-candidates/images --references P4/var/acceptance-candidates/references.json --compute-config P4/config/compute.cpu-heterogeneous.example.json --rounds 3 --out qa/integration/BENCH-cpu-RUNID
python P4/scripts/throughput.py measure --group gpu --config P4/var/control/center.json --inputs P4/var/acceptance-candidates/images --references P4/var/acceptance-candidates/references.json --compute-config P4/config/compute.cpu-heterogeneous.example.json --rounds 3 --out qa/integration/BENCH-gpu-RUNID
python P4/scripts/throughput.py measure --group pool --config P4/var/control/center.json --inputs P4/var/acceptance-candidates/images --references P4/var/acceptance-candidates/references.json --compute-config P4/config/compute.cpu-heterogeneous.example.json --devices P4/var/devices.json --rounds 3 --out qa/integration/BENCH-pool-RUNID
python P4/scripts/throughput.py compare --cpu qa/integration/BENCH-cpu-RUNID/throughput.json --gpu qa/integration/BENCH-gpu-RUNID/throughput.json --pool qa/integration/BENCH-pool-RUNID/throughput.json --out qa/integration/BENCH-compare-RUNID.json
```

`--config` 换成 A 实际启动数据目录中的中心配置（通常为 center.json），不把它复制进报告。测量命令在 A 运行，compute-config 是 A 的声明，工具另记录实际贡献节点的后端、槽数与预算并检查对比一致性。B 仍用 CUDA 配置。`devices.json` 按现有样例填写实际 worker_id、不同 physical_device_id 和人工确认。若使用运行时归一化 profile 副本，可用 `--profiles-dir` 指向它。

每组先记录 initial，再 warmup，再至少三轮正式数据。确实重启所测节点后才传 `--cold-start-confirmed`；模型加载时间从节点 model_loaded/准备日志单独记录，不把 initial 整个 Job 时间当加载时间。工具保留失败轮，不自动重跑掩盖失败。

- 完成吞吐量 = 唯一成功逻辑任务数 / P2 的 Job finished_at−created_at，单位张/秒。
- 正确吞吐量 = 通过冻结人工质量阈值的唯一图片数 / 同一时间窗口。失败、取消、重复尝试均不增加分子。
- 同时报客户端观测窗口（含轮询）和上传至完成耗时；不混用服务时间和客户端时间计算加速比。
- 正式结果取至少三轮中位数；分别保存每轮原始值、每节点贡献、执行次数、预取命中和实际参数。
- 双机加速比 = 池正确吞吐 / 最快单机正确吞吐；服务聚合比 = 池正确吞吐 / 两单机正确吞吐之和。后者不是本地执行器基准定义的聚合效率。
- 整机 CPU/RAM/GPU/显存约 3 秒采样，报告的是观测峰值，可能遗漏尖峰；未采到则留空。纯模型加载时间和更密集峰值需附节点日志/实机监测记录。

只有功能正确和完整质量基线通过后才能声称性能提升。未证明收益的可选项保持默认关闭。

## 停机升级与回滚

1. 先在 main 测试数据副本演练：停止新任务，排空/按既有语义取消，停止所有服务，确认计算进程退出。
2. 完整备份 P1/P2 数据库及 WAL/SHM（停机后复制整个数据目录）、输入/输出文件、连接配置、node install 身份、运行时 profile、解释器和依赖清单。备份留在私有目录；对外报告只记摘要。
3. 保留该快照不动，再复制一份给 0.4.0 中心/节点/工作台同时使用。启动两次验证幂等迁移，核对历史任务、原图和 ZIP，再跑 G0–G7 及已启用组合。禁止新旧进程写同一目录。
4. 回滚先全停新版本，另建目录恢复对应 main 快照、原环境和配置，启动冻结 main；验证旧任务/文件和新任务真实 OCR。不能只切旧代码读取升级后的库。
5. 通过后记录验收提交/标签、配置和全部证据，再将 zyc 提交供合入 main 审查。关闭可选配置只算运行方式回退，不算版本回滚。未完成实机门槛不宣称 S1–S7 正式通过。

本机历史数据副本检查可执行：

```sh
python P4/scripts/check_upgrade.py --main-tree /path/to/frozen-main-archive --source /path/to/stopped-main-run-local-data --private-dir P4/var/upgrade-RUNID --out qa/integration/upgrade-RUNID
```

此命令只接受 `run_local.py` 布局的停机测试副本，验证历史 Job、原图、结果和 ZIP 的新版本读取、重复启动及旧代码配套恢复。正式两台设备的停机升级、配置/身份迁移、回滚后新任务仍需按上面的步骤实测，不能用本机数据副本结果替代。
