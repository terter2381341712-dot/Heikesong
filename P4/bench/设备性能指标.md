# 在设备详情查看 CPU / GPU 吞吐量与效率

打开工作台 → 设备资源 → 设备列表 → 选择设备。CPU 与 GPU（CUDA）各有一栏。

PDF《D_Campus_Edge_Fabric_EN(1).pdf》第 2–3 页要求使用正确完成的有效工作量：

- 独立有效吞吐量 `Pᵢ = 正确完成图片数 / 单机测量秒数`。
- 池有效吞吐量 `Ppool = 正确完成图片数 / 池测量秒数`。
- 聚合效率 `η = Ppool / ΣPᵢ × 100%`。
- 相对最快单机的加速比 `S = Ppool / max(Pᵢ)`。

η 属于整个参与池，参与该池的各设备展示同一结果。混合 CPU/GPU 池的分母使用每台参与设备实际后端的独立基线，不把同一物理设备重复算成两台。CPU 和 GPU 配置需分别独立测量；没有 CUDA 或没有相应测量时显示“—”。效率超过 100% 保留原值并提示复核。

设备详情的“近期处理速度”选择最近 30 秒有结束记录或仍在执行的任务，以去重成功数除以这些任务首次执行至最后结束（仍运行则至现在）的实际墙钟时长。窗口内的间隔、失败和取消耗时保留在分母，并发槽共享同一窗口，不累加重叠执行时长。没有已完成样本时不猜速度；空闲 30 秒后清空近期样本。5 分钟长期平均仍保留在折叠项，明确标注成功数 / 300，包含空闲，不作为当前速度。

任务进度页新增各设备 CPU/GPU 运行表，约每 2 秒刷新，分别展示当前批次在每台设备及后端上的成功速度、CPU/GPU 利用率、正在执行数、成功数、单张执行耗时及已导入的基准池效率。本批次速度使用首次执行至最后结束的墙钟窗口，包含批次中途等待与失败耗时，不包含首次执行前排队；已结束批次保留自身测量结果。基准池效率不会伪装成本次任务的实时效率。缺少基线、质量核验或 GPU 采样时显示“—”。

速度计时为中心记录的精细时间戳，单张执行/推理耗时使用节点的计时；兼容已有数据库，旧记录没有可信后端时不补猜。失败、重传结果和重复任务不计入成功数。这些实时速度没有人工参考文本核验，不能替代 PDF 的有效吞吐量。整机平均利用率按近 300 秒实际收到的心跳样本计算，目标间隔 3 秒；任务页的利用率是最新心跳读数。

关闭上传或进度弹窗只切换页面，已经开始的上传提交继续进行，已受理任务由 P2 后台调度。首页新增后台任务入口并继续跟踪状态。取消任务需点击“取消任务”；关闭整个浏览器前应确认服务器已经返回 Job ID，未传完的本地文件无法在浏览器退出后继续上传。

## 生成并导入有效吞吐量报告

沿用本目录 README 的质量准备步骤：至少 20 张内容不同、来源许可明确的图片；事先冻结人工参考文本和 CER 阈值。每个实验使用相同源码、输入字节、正确性标准、任务 profile 和参数。固定槽位、线程和设备集合，每组预热后至少 3 轮，取各轮吞吐量中位数。

以下在项目根目录执行，Windows 使用私有 Python 3.9.6。`client.json` 必须指向当前中心并包含当前用户令牌；具体生成方法见 P4 部署文档。各 `--out` 目录必须尚不存在。

```powershell
# 先暂停其他设备，仅保留被测 CPU 设备共享
.\P4\var\runtime\P1\python.exe P4/scripts/throughput.py measure --config P4/var/config/client.json --inputs P4/var/inputs --references P4/var/references.json --group cpu --rounds 3 --out P4/var/perf-cpu-A

# 仅保留被测 CUDA 设备共享，使用匹配的异构 profile 配置
.\P4\var\runtime\P1\python.exe P4/scripts/throughput.py measure --config P4/var/config/client.json --inputs P4/var/inputs --references P4/var/references.json --group gpu --compute-config P4/var/compute.json --rounds 3 --out P4/var/perf-gpu-B

# 开启固定参与设备，核对 devices.json 的真实设备映射，确认输入足量
.\P4\var\runtime\P1\python.exe P4/scripts/throughput.py measure --config P4/var/config/client.json --inputs P4/var/inputs --references P4/var/references.json --group pool --compute-config P4/var/compute.json --devices P4/var/devices.json --sufficient-load-confirmed --rounds 3 --out P4/var/perf-pool
```

macOS/Linux 用 `P4/var/runtime/P1/bin/python`。如通过按钮启动，`--profiles-dir` 必须选中心实际发布的 profile 目录，避免源文件 CRLF 与运行副本 LF 摘要不一致。全组使用同一 profile；纯 CPU 实验不需要 GPU 那条命令。多台 CPU 设备需逐台生成独立报告，不能只测一台就作为所有机器的基线。

在设备详情点“导入单机及池测量报告”，一次选择所有参与设备的单机 `throughput.json` 及池 `throughput.json`。服务会验证输入集、正确性、测量窗口、至少三轮、设备执行配置和后端一致，再从数量/时长重新计算；导入会替换当前测量组，重启后保留。需要有效的用户令牌。接口为 `GET/POST /api/resource/v1/performance`。

这些基线使用单设备端到端服务路径，包含调度开销；界面不将其声称为纯本地执行器性能。正式提交仍需保留 PDF 要求的本地完整执行器基线、全部原始证据、设备配置及负载说明，见本目录 README。尚未在两台物理设备和真实 CUDA 上完成现场性能验收。

## 另一台电脑提示自动准备失败

保持 Python 3.9.6。换电脑会重新准备该电脑自己的私有运行环境，`var` 不随 Git 上传是正常的。截图中的“自动准备未完成”只是总提示，不能据此判断网络、依赖安装还是 DLL 导入失败。

新版将当前安装步骤、pip 错误以及安装后的实际模块导入错误写入 `P4/var/runtime/setup.log`，并在“本机控制 → 服务日志 → 环境准备”显示。pip 下载增加超时与重试；再次启动会重新检查。预览版本的日志位于该预览副本下的 `P4/var/runtime/setup.log`。若仍失败，保留日志末尾 60 行用于判断具体原因；不要复制另一台电脑的虚拟环境。
