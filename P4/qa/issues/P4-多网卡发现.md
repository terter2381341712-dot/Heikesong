# P4-DISCOVERY-001：多网卡导致中心发现地址错误

2026-11-14，Windows 中心已启动，但本机发现列表显示 VMware VMnet8 的 `169.254.69.129:8003`，Mac 没有自动发现中心。两端配对码此前一致，不能据此归因于配对码。

现场确认：

- Windows WLAN 地址为 `10.4.142.66`，中心配置的 P1/P2 服务地址也使用该地址。
- Mac 执行 `curl --connect-timeout 5 http://10.4.142.66:8001/api/resource/v1/healthz`，返回 `p1_resource`、`status: ok`。
- Mac 在页面手动输入 `10.4.142.66:8003` 并使用中心当前配对码后，用户确认“连接成功”。这证明跨机 P1 健康接口和控制台配对连接可用；尚不能据此认定跨机 OCR 或正式验收通过。

原发现逻辑使用单个未绑定网卡的 UDP 广播套接字，并直接将回复数据包的来源 IP 当作中心地址。多网卡环境可能从虚拟网卡回复，导致来源 IP 与实际服务地址不一致；单次广播也可能走到错误的网卡。现场尚未证明 UDP 广播是否另受防火墙或无线网络限制。

本次仅修改 P4：

1. 中心回复包含启动时选定的服务地址及本机身份。客户端使用声明的服务地址，不再依赖回复的网卡地址。
2. 各可用私有 IPv4 网卡分别发送广播，合并重复中心；拒绝 `169.254.*`、回环等不可作为中心入口的地址。
3. 加入节点列表排除本机中心；旧版回复在缺少身份时按名称兼容判断。
4. 中心配对码旁显示可供另一台电脑填写的地址。

回归命令（项目根目录）：

```powershell
P4/var/python39/python.exe -B -m pytest -q P4/tests --basetemp=P4/var/pytest-discovery-fix --junitxml=P4/qa/discovery-pytest.xml
```

结果：59 PASS / 1 SKIP，Python 3.9.6。覆盖虚拟网卡来源、声明地址、旧版兼容、身份排除、各网卡广播、去重，以及独立临时端口的真实 UDP 请求/回复。跳过项为既有 POSIX venv 测试。Ruff 检查通过。测试未停止用户正在运行的中心。

部署后待复验：两台电脑同步最新 P4，分别在原启动终端 Ctrl+C 退出后重新启动，检查 Mac“查找中心”能否显示实际 WLAN 地址。当前正在运行的旧进程不会因为文件更新或刷新网页而加载新版发现逻辑。若 UDP 广播被网络限制，仍可用页面内手动地址完成配对，无需复制配置文件。

后续计算验证：中心设备列表确认 Mac 在线并开启共享，再点“测试两张图片”。两张图成功仍不保证两台都被调度；正式双机贡献需要核对两台节点的执行记录。
