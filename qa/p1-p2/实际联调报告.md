## 本轮实际改动及原因

1. 将 P1 所属源文件原样放入独立 `P1/`，补来源记录与适应本地目录的 README，安装其独立依赖环境。没有重构 P1 或修改模型锁文件。
2. 新增 [run_local.py](run_local.py)，显式传入同一资源服务地址、独立数据目录、匹配的 profile 目录和各角色所需令牌。P2 不收到 JOIN_TOKEN，节点不收到 DEMO/TASK_TOKEN。
3. 解决实际启动失败：本机继承的 IPv6 `NO_PROXY` 条目使 P1 的 httpx 0.28.1 客户端在构造时抛出 `InvalidURL: Invalid port: ':1]'`。相同环境的单独客户端构造可复现；仅在本机联调子进程中覆盖 `NO_PROXY/no_proxy=127.0.0.1,localhost` 后成功。没有改系统代理或 P1 网络实现。
4. 工具按 `(task_type, profile_id)` 查找 OCR 能力。真实 P1 更新能力后，数组中 ASR 可位于 OCR 前方；此前工具取第 0 项导致一次已成功的 OCR 检查误报。P2 原有匹配逻辑正确，无需修改。
5. 工具保留调用关联、状态与真实结果，失败/中断非零退出，停止自己启动的进程，防止同数据目录重复启动；补 9 项工具回归。原有服务、数据及工作区未提交迁移保留。

没有新增公共字段、状态或路由，没有放宽 schema、结果 SHA、输入关联或 READY 证据校验，也没有执行远程合并、提交或推送。

## 输入输出与数据流核对

客户端以 DEMO_TOKEN 上传真实 PNG 到 P1，取得 INPUT Artifact；用目录中的冻结 profile/digest 和 artifact IDs 向 P2 创建 Job。P2 自动发现 NOT_PREPARED/null 节点，请求准备并等待真实自测通过，再逐图派发 execution。

P1 实际生成 OCR JSON 及 RESULT Artifact；P2 拉取并严格校验后持久化，提供按输入顺序排列的 results 与 ZIP。本轮记录核对了 job/task/execution/preparation/worker/session、输入 SHA、profile digest、结果大小与 SHA。两服务重启沿用各自数据目录。
