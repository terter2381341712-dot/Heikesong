# 第三阶段：资源感知调度实施报告

2026-11-14，Stage 1、Stage 2、Stage 3 均保留在 `zyc` 分支。当前代码已完成本机测试和真实 CPU 联调，后续由项目所有者决定何时合入 `main`。

## 实现与兼容性

P2 在原有剩余槽位约束之上，先检查 CPU/CUDA 实际 provider、profile/digest、自测和线程预算，再按成功执行的下载、推理及其他开销估计耗时。没有可用槽的节点不进入候选；GPU 没有固定加速倍率，实测较快的 CPU 可以优先。

历史按节点、后端、模型、槽/线程配置和图片规模隔离，默认使用最近一小时内最新 32 条样本及指数加权平均。没有有效历史时使用已通过自测的耗时先验；每第 8 次派发保留探索机会，并可预热一个尚未准备的节点。资源快照中已经计入的执行不重复扣槽，未确认的接纳请求继续保守占槽。

调度决策与执行请求一起落库，成功样本与校验后的结果一起提交。失败、取消、无效结果、异常或过期耗时不参与学习。P2 重启保留历史，同一 execution_id 不会重复采样。新增的 scheduling_decisions / scheduling_samples 是内部 SQLite 表，不改变 Job 响应或导出内容，公开契约仍为 **0.3.0**。

独立对账与结果下载使用有界并发和超时。不确定节点暂不接新任务，健康节点继续工作；已成功但结果待取回的执行不继续占用计算槽。P1 的取消、共享关闭、停止确认和迁移协议保持不变。

详细配置、估计公式、边界和诊断方式见 [资源感知调度说明](../../P2/docs/资源感知调度.md)。主要代码为 [scheduling.py](../../P2/task_service/scheduling.py)、[service.py](../../P2/task_service/service.py)、[store.py](../../P2/task_service/store.py) 与 [config.py](../../P2/task_service/config.py)。

## 真实观测

资源调度运行目录：`qa/p1-p2/var/resource-scheduling-6326855f`。一台 macOS 物理电脑启动两个 CPU Agent：一个节点为 2 槽 × 1 线程，另一个为 1 槽 × 2 线程，通过实际 HTTP、RapidOCR 与 ONNX Runtime 完成任务。

- 初始准备后，两节点均执行了真实图片任务；记录了 9 条成功样本。
- 重启 P2，历史及派发序号完整保留。随后 3 个单图 Job 都使用 execution_history 排序，选择历史估计耗时更低的节点。第一次选择的评分约为 408 ms，另一候选约为 695 ms；这些是派单时的估计评分，不是加速比或时限承诺。
- 一张 1600×1000 图片进入新的像素桶，正确回退 calibration，未复用小图桶的历史。最终共 13 条真实成功样本，execution_id 全部唯一。
- 记录含每次决策的候选评分、估计来源、后端、剩余槽数和调度模块 SHA，已经核对与当前代码一致。

取消与迁移运行目录：`qa/p1-p2/var/multislot-e4772018`。真实大图同时进入两个不同的 CPU 模型进程；取消一个 Job 只重建其槽，另一个槽保留模型并成功完成。后续关闭共享时，两项未完成任务迁移到另一 Agent，已完成的小图结果保持原值，最终尝试数为 **1 / 2 / 2**。

迁移测试脚本补充处理了合法的 DISPATCHING 窗口：P2 已持久化执行 ID、P1 尚未接纳时不立即查询 RUNNING，从而避免把该窗口的 404 误判成服务故障。

## 复跑

在项目根目录执行，环境沿用前两阶段说明：

```sh
(cd P1 && .venv/bin/python -B -m pytest tests/resource -q)
(cd P2 && .venv/bin/python -B -m pytest tests/tasks ../qa/p1-p2/test_run_local.py -q)
P2/.venv/bin/python -B qa/p1-p2/check_resource_scheduling.py
P2/.venv/bin/python -B qa/p1-p2/check_multislot.py
```

默认配置已补充到 [P2/.env.example](../../P2/.env.example)，实际启动需由 shell 或进程管理器注入，不会自动读取该文件。
