## 0. 结论先行

这是一个**竞赛项目**（D 题「真实设备组网 / Campus Edge Fabric」）：把多台真实电脑的空闲算力组成算力池，共同完成批量图片 OCR，赛题要求 ≥2 台独立物理设备对同一 Job 贡献有效计算 [证据: D题参赛执行包/sources/已读赛题依据.md:7-20]。

系统由**四个可独立部署的模块 + 三套支撑目录**组成：

| 层 | 模块 | 端口 | 一句话职责 |
|---|---|---|---|
| 资源层 | P1 `resource_service` | 8001 | 设备/文件/模型/单次执行 |
| 任务层 | P2 `task_service` | 8002 | Job 拆分、调度、对账、汇总 |
| 交互层 | `web` Edge Fabric 工作台 | 5173 | 上传、进度、结果、本机控制 |
| 集成层 | `P4` 控制台与验收 | 8003 / UDP 37043 | 一键启动、双机配对、验收取证 |

核心边界：**P2 单向调用 P1，P1 绝不调用 P2；节点只主动出站连 P1，没有入站监听** [证据: P2/task_service/p1.py:9,25-33；P1 README.md:49；P4/README.md:27,64]。全系统唯一 HTTP 字段规范是 `openapi.yaml` **0.4.0**，P1/P2/执行包三份副本字节完全一致（SHA-256 `2efab40f…`，各 3116 行）。

当前状态：**本机代码与回归全绿，正式双机 / CUDA 实机 / 质量 / 性能门槛全部 NOT_RUN**；多个 README 与执行包文本仍停留在 0.2.0/「尚未实现」，属历史滞后 [证据: qa/integration/implementation-summary.json:30-32；P4/集成发布说明.md:13]。

## 1. 项目定位与分工由来

- 业务场景：批量文档、学术图表 OCR；一图一 Task；结果导出 ZIP（`manifest.json` / `results.json` / `combined.txt` / `results/*.json`）[证据: D题参赛执行包/06-项目概况与OCR任务补充声明.md:28,36,40-52]。
- 团队按 **P1/P2/P3/P4 四人并行分工**，不是四个串行阶段：P1 资源接入与执行、P2 任务分析与调度、P3 前端、P4 契约发布与联调验收 [证据: D题参赛执行包/README.md:11-18]。
- 责任唯一归属（设计契约）：P1 拥有设备、会话、硬件、心跳、文件字节、模型配置、单次执行；P2 拥有 Job、逻辑 Task、输入顺序、节点选择、业务重试预算、最终聚合；P3 只消费 HTTP、不改写业务事实；P4 只出证据、不回写状态 [证据: D题参赛执行包/02-架构与接口说明.md:29-39]。
- 追溯链：`client_request_id → job_id → task_id/input_index → execution_id/attempt_no → worker_id/session_id → 输入 SHA/profile_digest → 结果 artifact SHA` [证据: D题参赛执行包/02-架构与接口说明.md:57]。

## 5. 核心功能清单

1. **契约驱动的双服务架构**：OpenAPI 3.1.0 / 0.4.0 定义 14 个 P1 端点 + 7 个 P2 端点，P2 直接加载 YAML 用 JSON Schema 校验请求与响应，不另建模型。
2. **真实多设备算力池**：节点主动注册、3s 心跳、租约、失联 15s 判离线、`ACTIVE/DRAINING/PAUSED` 三种模式；P4 连接码 + 六位码实现跨机配对 [证据: P4/一键连接.md:35-37]。
3. **一图一 Task 的批量 OCR**：单 Job 1–200 张 JPG/PNG，按 `input_index` 保序，结果 JSON/TXT/ZIP 有序汇总。
4. **资源感知调度**：`round_robin`（当前默认）与 `resource_aware` 双策略；后者按像素分桶 + 历史耗时 EWMA(α=0.3) 预测 + 占用惩罚评分，周期性探索冷节点 [证据: P2/task_service/scheduling.py:85-175；P2/README.md:1]。
5. **共享开关与任务迁移**：关闭共享立刻中止本机在途工作，已成功结果保留，未完成 Task 由 P2 重新排队（最多 3 次）到其他节点。
6. **异构算力**：CPU 多槽（进程级隔离 + 线程预算）、GPU 逻辑多 lane（一份权重 + 推理锁 + 显存预算）、单槽输入预取与解码/推理重叠、CPU/CUDA 常驻模型。
7. **幂等与崩溃恢复**：`client_request_id` 幂等创建、原 ID 原载荷重放对账（GET 404 / 5xx / 超时绝不另开执行）、P1/P2 重启恢复、结果 SHA-256 + bbox 越界校验、事务内写状态与结果。
8. **端到端取证**：`verify.py` / `quality.py` / `throughput.py` 产出可追溯 JSON/JSONL/CSV/ZIP，明确区分「执行成功」「业务质量」「正式性能」三者。
9. **双模式前端**：真实模式代理到 P1/P2；MOCK 模式离线演示，显式标记，不污染正式证据。

### 6.4 数据与契约依赖

- **契约单点**：`D题参赛执行包/contracts/openapi.yaml` 是唯一维护源，P4 是唯一落盘维护人；P1/P2 各存一份不可修改的副本；任何一方改字段需升版本并三处同步 [证据: D题参赛执行包/README.md:45-49；P2/contracts/README.md]。
- **两份独立数据库**：P1 `resource.sqlite3`（8 表）与 P2 `tasks.sqlite3`（5 表），不共享表、不 import 对方业务模块。
- **文件身份链**：P1 保管原图与结果 artifact 字节（SHA-256），P2 只持 `artifact_id` 与元信息，避免跨机传绝对路径。
- **profile fingerprint**：锁文件原字节 SHA-256 作为 `profile_digest`，Job 创建时冻结，节点准备与执行全程比对，防止不同机器模型不一致。

## 7. 端到端数据流（一次 OCR 任务）

1. 浏览器 `POST /api/resource/v1/artifacts`（multipart）→ P1 落盘 `artifacts/{id}.bin`，返回 `artifact_id` + `sha256`。
2. 浏览器 `POST /api/task/v1/jobs`（`client_request_id`、task_type、profile_id/profile_digest、artifact_ids）→ P2 校验幂等。
3. P2 `P1Client.catalog()` 校验类型已 `CONFIGURED`，逐 artifact 拉元信息 → `splitters.ocr.split_images()` 一图一 Task → 冻结 profile 落 SQLite，Job `QUEUED`。
4. `TaskService.tick()` 每轮：`revoke_invalid` → `_recover_work` → `GET /resources` 取资源快照 → 算剩余容量 → `candidate_action()` 资格门（ONLINE/ACTIVE/无清理/空槽/READY 证据/线程预算）→ `Scheduler.choose()` 选节点。
5. 若节点 `NOT_PREPARED`：P2 `POST /preparations`；节点加载锁文件、三张合成图真实自测、上报 READY（backend/provider/model_sha256）。
6. P2 事务内先持久化完整 `requests` 与 `scheduling_decision`，Task 置 `DISPATCHING`，再 `P1Client.reconcile("executions", …)`：GET 原 ID，404 则原载荷 POST 重放；**先落库再发请求**。
7. P1 接单占槽 → 节点 `claim` 领取 → 从 P1 下载原图（校验 SHA）→ 本地 RapidOCR/ONNX 推理 → `POST /complete` 把结果写回 P1 成为 RESULT artifact。
8. P2 `_reconcile_task()` 拉执行状态 → `P1Client.result()` 下载结果，校验长度/SHA-256/`OCRResult` 结构/`input_artifact_id`/宽高/bbox → 同事务写 `results` + Task `SUCCEEDED` + 调度样本。
9. `Store.refresh()` 由 8 种 Task 计数派生 Job 终态（`SUCCEEDED` / `PARTIAL_FAILED` / `FAILED` / `CANCELLED`）。
10. 浏览器 `GET /jobs/{id}` 看逐图进度、`GET /results` 预览 `combined_text`、`GET /download` 取 ZIP。P4 控制台另有「测试两张图片/自选图」走 `verify.py --inputs` 并复制结果 ZIP 供下载。

**异常路径**：节点关闭共享或掉线 → P1 标 `CANCELLED`/`NODE_UNAVAILABLE`/`retryable` → P2 `_record_execution()` 若 `attempts_used<3` 把 Task 退回 `WAITING_FOR_RESOURCES` 并设 `retry_at`，下轮改派他机；普通取消不重排队，已成功结果保留。

## 8. 现状、矛盾与风险（必读）

1. **文档版本滞后**：执行包 README/任务卡、架构说明、`P2/pyproject.toml` 描述仍写 0.2.0；实际契约 0.4.0 [证据: D题参赛执行包/README.md:3；P2/pyproject.toml:4；三份 openapi.yaml:4]。
2. **README 自相矛盾**：`P1/README.md:13` 写「共享开关尚未实现」、`:41` 写「尚无安装器或桌面共享开关」，但 `service.py:1029` 与 `P4/control.html` 均已实现；各 README 顶部「阶段更新」块才是有效的当前状态，正文多为历史追溯。
3. **正式验收未完成**：两台独立物理设备同 Job 贡献、CUDA 实机、CER 质量、正式吞吐门槛全部 `NOT_RUN`；本机单槽三轮中位完成吞吐仅 0.684 张/秒且标 `MEASURED_NOT_ACCEPTED` [证据: qa/integration/README.md:15,19-21；P4/集成发布说明.md:13]。
4. **ASR 是空壳**：`asr.file.v1` 在 `task_types.json` 中始终 `UNCONFIGURED`，Runner 只有 `DevStub`；当前只开放 `ocr.image.v1`。
5. **GPU 多 lane 不可直接启动**：`compute.cuda-multilane.example.json` 故意把 `gpu_lane_vram_bytes` 留空，必须实机 `gpu_probe` 填实测显存；契约目标 0.5.0 尚未发布。
6. **分支未合并**：当前在 `zyc` 分支，`lt`/`lyj` 已并入 `main`，三分支无共同祖先不能直接 `git merge`；`merge_commit_created=false` [证据: 分支合并评估报告.md:6,12-19；implementation-summary.json:32]。
7. **兼容债**：根目录 `.venv`、`var` 是迁移遗留符号链接；`P2/.venv-runtime` 只服务旧后台进程；新开发应从 `P2/` 用 `P2/.venv`。
8. **代码分层不纯**：P1 的 `node_agent` 反向复用 `resource_service` 工具模块，`rapidocr_runner` 又反向引用 `node_agent.input_pipeline`；P2 几乎所有模块汇聚到 `contract.py`（可接受但改动影响面大）。
