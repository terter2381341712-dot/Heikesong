## 3. 历史与差异的正确解读

当前祖先包含关系：`lyj@68677c8 → … → lt@18ad887 → main@0dd6ca5`。这里的箭头表示可达关系，省略了中间提交和合并。

zyc 与 main、lt、lyj 的共同祖先均为初始提交 `47063c4a42351f5d50bead306fd50916689a5502`。因此许多实际上内容接近的 P1/P2 文件，在 Git 历史中属于两边分别新增，而不是在近期共同代码上修改。这是 add/add 冲突集中的原因；不属于无共同祖先，不需要 `--allow-unrelated-histories`。

从 main 快照到 zyc 快照的直接差异为 **224 个文件、23,632 行新增、13,079 行删除**，具体组成：

| 类别 | 文件数 | 说明 |
|---|---:|---|
| 仅 zyc 有 | 64 | 新后端模块、测试、报告、资料等 |
| 仅 main 有 | 116 | 包含 P4 83 个文件、web 31 个文件及两份 .gitattributes |
| 两边都有但内容不同 | 44 | 与本次 main+zyc 的冲突文件集合一致 |

**快照 diff 中的 D 不代表正常合并会删除 P4/web。** zyc 从未加入这些文件；三方合并会保留 main 独有文件。整目录覆盖或把 zyc 的整棵树当作合并结果，才会丢失它们。

## 4. 各分支改动范围

### zyc：P1/P2 计算与调度升级

相对远程 main：P1 有 21 个同名文件变化和 16 个独有新增文件；P2 有 15 个同名文件变化和 7 个独有新增文件。主要能力如下：

- P2：资源感知调度、剩余容量派发、并发与 I/O 超时控制、调度历史和样本记录、输入预取协同。新增 `task_service/scheduling.py` 和 `prefetch.py`。
- P1/P2 数据库存储结构增加槽位、预取、调度决策/采样相关内容。
- 公开契约从 main 的 0.2.0 升到 0.4.0，同时更新三份 OpenAPI、样例、类型目录和后端版本断言。

zyc 独有的 6 个提交为 `3444af5`、`cf6214a`、`6d465ad`、`b51bb13`、`9e18152`、`8690c3c`；早期包含执行包和大批后端导入。因此只 cherry-pick 最后一个提交会缺少依赖，完整逐个 cherry-pick 又会重复遭遇大量同名文件冲突。

核心为 `web/`：真实 OCR 与 MOCK 模式、API 代理、任务进度、结果下载、粒子交互、中英文界面、令牌验证/复制、自选图片验收、设备控制台嵌入和断线交互。同时整合 P4 启动流程，并携带主线 Windows 启动、共享状态等修复。

### lyj：P4 启动、配对、验收与演示

该分支也包含当时的 P1/P2 Python 3.9.6 环境统一和相关配置变动，不应只按“只改 P4”理解。其 9 个阶段提交（从 `a913a30` 到 `68677c8`）已经进入 main 历史。lyj 本身没有 `web/`，完整前后端体验应以最新 main 为基线。

## 8. 推荐合并顺序与操作方案

### 推荐：以远程 main 为底座做一次人工集成

1. 固定本次四个远程 SHA；执行合并前再 fetch，若分支推进，重跑差异和试合并。保留本地 main 的引用备份及工作区原有文件。
2. 在独立 worktree 从 `origin/main` 新建 `codex/integrate-zyc-main`；不以过时且分叉的本地 main 开始。
3. 合入 `origin/zyc`。此时 main 已经包含 lt/lyj，无需重复 merge。
4. 先统一契约/schema/profile 与存储，再整合 P1 运行时和 P2 调度；保留 main 的三类已知修复：Windows stdin、Windows Uvicorn 入口、共享关闭模式保护。
5. 保留 main 的 P4/web 和 `0dd6ca5` 路由修复；同步 P3/P4 到约定契约版本，扩展多槽/GPU/profile 参数透传及相关测试。
6. 合并文档与来源记录，保留换行约束；检查自动带入的 `.DS_Store`、无关 PDF 和历史大体积报告是否应纳入最终交付。
7. 完成下面的验收后，以 PR 合入 main。合并成功后，团队再将新 main 同步回开发分支，减少再次从初始提交分叉造成的冲突。

准备命令示例（本次未执行）：

```sh
git fetch origin --prune
git branch backup/main-before-integration-20261115 main
git worktree add -b codex/integrate-zyc-main ../heikesong-integrate origin/main
git -C ../heikesong-integrate merge --no-commit --no-ff origin/zyc
```

最后一条按本次快照会停在预期的冲突状态，需完成上述人工整合。执行前检查示例备份名、分支名和目标目录是否已存在。不要通过 `reset --hard` 或强推处理当前本地 main 分叉；需要继续使用本地 main 时，在保留其独有历史后再决定如何同步。

### 其他方案的评价

- **先合 lt 再合 lyj：** 对当前 main 无新增收益，两者已经被包含。
- **先 zyc+lyj，再加 lt：** 第一阶段已有 44 个冲突，后续还要处理前端和主线修复，工作量更大。
- **对所有冲突统一选 ours：** 会让 zyc 新增模块与旧后端/旧契约混合，多槽功能不完整。
- **统一选 theirs 或直接覆盖 P1/P2：** 会丢主线修复，并保留未升级的 P3/P4；已通过实验确认不可靠。
- **只 cherry-pick 8690c3c：** 缺少前序常驻模型、多槽、预取和调度基础，不适合作为完整合并。
- **分阶段迁移功能：** 若团队希望缩小每次审核范围，可按常驻模型→CPU 多槽→资源调度→预取→GPU 逻辑路拆分，但现有提交粒度较大，需要重新组织补丁与契约发布，成本高于一次有计划的集成。

### 合入 main 前的验收门槛

- P1/P2/P4 全量测试与控制台 JS 回归；主线共享关闭保护、Windows 启动回归保留。
- 三份 OpenAPI 字节一致；examples、类型目录、fixtures、API 健康、结果 ZIP manifest、前端和验收脚本版本一致。
- 真实浏览器：中心启动、节点配对、令牌验证、自选图片上传、任务进度、结果/原图/ZIP 下载，尤其复验远程配对节点的工作台代理。
- CPU 单槽/多槽，线程预算，常驻模型，取消、共享关闭、迁移、重连/重启，不能发生旧执行结果覆盖新槽位代次。
- 旧库副本升级与重启恢复；记录备份/回滚所对应的代码和数据版本。
- GPU 路径在 Windows NVIDIA 环境单独验证：正确解释器/profile、CUDA provider、单槽/多路 N=1/2/4、显存峰值、取消恢复和吞吐对比。未验收前默认保守配置，不声称已有真并行 GPU 加速证据。
- 两台物理设备共同完成同一任务；区分本机多进程测试与物理多机验收。
