# P1/P2 设备共享开关与任务迁移补充计划

日期：2026-11-14。状态：**用户需求已确认；以下实施方案待双方开发与联调，当前代码尚未实现。**

本文件补充 [统一修改计划 1.0](P1-P2统一修改与联调计划.md)。用户在基础连接验证期间明确：安装 PE（本文对应 P1 节点客户端）时选择调度中心，安装后不自动贡献资源；用户打开共享才允许接单；**关闭共享要立即停止本机当前工作，保留已成功结果，将未完成图片交给其他可用电脑。** 用户明确选择此行为，取代把共享开关解释成“完成当前任务再暂停”的建议。

现有 `DRAINING` 仍表示排空并完成已接工作，原有 Job 取消仍表示取消整批。新增的“关闭设备共享”不能复用这两种操作而改变它们的既有含义。基础联调的通过范围见 [实际报告](qa/p1-p2/实际联调报告.md)，不能据此声称本补充已完成。

## 1. 已确认的用户体验

1. 安装、打开应用或保存中心地址均不自动加入计算池；首次默认关闭共享。
2. 用户可以保存多个调度中心地址，每次选择一个；同一设备的同一执行器同时只加入一个中心。
3. 打开共享后，客户端向选定中心注册并发送心跳、设备能力与资源状态。中心能看见该设备，模型准备合格后参与调度。
4. 关闭共享时立即禁止新工作，并触发本机当前模型准备/识别的终止；不能依赖停止心跳后等待失联超时来代替主动关闭。
5. 关闭不取消整个 Job。已经成功的图片继续保留；未完成图片转交其他可用设备，无资源时等待。再次打开可重新加入。
6. 切换中心先完成旧中心的撤出和旧计算停止；不能同时为两个中心运行同一个计算槽。

“在线”“允许接单”“正在清理/停止”分别表达不同事实。共享已关时，即使进程还在线或正在确认停止，中心也必须显示“未共享/正在停止”，不得显示可接单。网络断开则走现有失联与撤权流程，不能假称已同步成功。

## 2. 100 张图片的明确行为

沿用现有“一张图片一个 Task、每节点一个槽”。100 张是一个 Job，不是一次给节点塞入 100 张不可分割的计算。

| 关闭瞬间的图片 | 处理 |
|---|---|
| 第 1–55 张已被 P1 原子发布为 SUCCEEDED | P2 保留已持久结果；若仍未下载，继续按原 execution/artifact 下载并校验，不重新识别 |
| 第 56 张正在计算 | P1 撤销结果提交权并终止计算；确认停止并发布明确终态后，P2 将同一个 Task 重新排队，使用新的 execution_id 调度 |
| 第 57–100 张尚未执行 | 保持等待任务，调度到其他已开启共享的合格节点 |
| 没有其他可用节点 | Job 保持等待资源，55 张结果仍能查询，其余 45 张不会消失或被计为成功 |

关闭与成功发布存在竞态：若第 56 张先原子发布成功，应保留它，只迁移 44 张；若关闭先撤权，则拒收这次执行之后的结果，迁移 45 张。以中心已持久的权威结果为准，不能仅依据按钮点击时显示的计数。

## 3. 中心地址、心跳与接口边界

面向用户可以统一称“P2 调度中心”。中心部署包含 P2 任务服务和 P1 中心资源服务；每台计算电脑安装 P1 节点客户端。现有数据流继续为：

```text
设备上的 P1 客户端 ──注册/心跳/领取已分配工作──> 中心 P1 资源服务
                                                       ↑
                                      P2 读取资源、准备、派发和取结果
```

- 当前节点 `--server` 接收资源服务地址（默认端口 8001），**不能直接填当前仅提供任务 API 的 8002 地址**。
- 若安装界面必须只填一个中心 URL，部署方应提供统一入口，将 `/api/resource/` 路由到资源服务、`/api/task/` 路由到 P2；中心选择保存该入口及加入凭证。这是待实现的部署适配，当前没有这样的网关。
- 节点主动连中心即可接收已分配的工作；P2 使用 `worker_id/session_id` 调度，无需反向连接每台电脑的 IP/监听端口。IP 如需展示，应作为单独的诊断信息设计，不能擅自塞进 0.2.0 ResourceNode。
- 注册、心跳和设备自身的开关控制仍由 P1 内部协议负责，P2 只读公开资源与执行接口。节点只持有加入/自身会话凭证，不分发 TASK_TOKEN 或 DEMO_TOKEN 给每台设备。
- 客户端配置及稳定身份按中心隔离；旧中心的 worker、session、秘密凭证不能误用于新中心。

## 4. 双方共同采用的状态约定

以下为后续实现目标，现有公共模式操作的行为不在本次基础联调中修改。

### 开启

P1 先确认本机没有上一中心或上一会话的计算残留，然后注册/恢复合法会话，发布 ACTIVE 和真实能力；新会话重新核验后才 READY。P2 沿用统一计划的准备、槽位与派发检查。

### 关闭

1. 本机立即禁止领取新工作，并向中心提交带自身会话认证的关闭请求。P1 提供可重复调用的内部控制操作，不能让节点调用需要全局任务令牌的公开控制 API。
2. 中心原子地将该节点设为 PAUSED、`available_slots=0`，撤销其活动工作的提交权并持久化“用户关闭资源共享”的原因。排队、未领取、已运行和模型准备均不能漏掉。
3. P1 使用可终止的模型子进程或其他能确认终止的机制停止真实计算。仅改状态、忽略识别结果或等待整次识别自然返回，不满足本需求。
4. 计算尚未确认停止时保持清理屏障，不得宣称已恢复可接单；开启也不能绕过这个屏障。中心未收到停止确认且终态不明确时，P2 保留原请求对账，不凭一次超时换 ID。
5. 停止确认后，P1 对该次执行发布 `CANCELLED`，并以结构化 Error 指明共享关闭。已成功的执行保持原终态及文件。
6. P2 识别主动撤出原因后，仅将对应未成功 Task 恢复到 `WAITING_FOR_RESOURCES`；Job 保持进行中。保留原 execution 的历史记录，下一次派发使用新 ID，Task/输入/profile 不变。

### 兼容的取消原因约定

为避免临时添加字段或错误枚举，建议双方统一使用现有 0.2.0 schema 可表示的组合：

| 情况 | Execution 与 P2 行为 |
|---|---|
| 设备主动关闭，且停止已确认 | `status=CANCELLED`；`error.code=NODE_UNAVAILABLE`、`error.retryable=true`、`error.details.execution_id` 为原 ID；message 说明共享已关闭。P2 在 Job 未请求取消时允许重新调度 |
| 用户取消整个 Job | P2 的 `job.cancel_requested=true` 优先，不迁移，不创建新 execution；已有成功仍保留 |
| 原有 CANCELLED、无明确主动撤出原因 | 继续现有终止语义，不把所有取消都改为重试 |
| 取消未确认、执行状态未知 | 保留原 ID 查询/重放，不启动重复计算 |

上述组合是**双方待实现的新增语义**，不是当前 P1 已经提供的能力。公开 Error.code 是枚举，不能由任一方自行添加 `NODE_SHARING_DISABLED` 等新值。若后续选择新字段或新错误码，必须先统一修订主契约及双方副本、样例和测试。

本补充的最小实现仍受原契约“最多 3 次已接受尝试”约束；主动中断也不能抹掉已接受记录或倒退 attempt_no。用户给出的首次中断场景可以在第二次尝试接续。若产品要求多次设备撤出后仍无限迁移，需要另行修订计数语义和契约上限，不能在当前 schema 下伪造次数。

## 5. 修改责任与当前缺口

| 责任方 | 当前情况 | 待完成 |
|---|---|---|
| P1 客户端 | 启动就注册；无中心选择界面和共享开关 | 保存中心、默认不共享、显式开关、每中心身份隔离；关闭时立即触发停止及上报 |
| P1 执行器 | 识别在节点工作循环里同步运行；取消确认要等计算返回 | 可终止计算、停止确认、禁止旧结果提交；开关关闭与模型准备也联动 |
| P1 中心资源服务 | 有 ACTIVE/PAUSED/DRAINING，但普通模式切换不代表主动中止工作 | 自身凭证控制入口、关闭原因持久化、原子撤权及终态、重放/重启恢复 |
| P2 | 已有逐图 Task、成功结果持久化、无资源等待；CANCELLED 当前直接结束 Task | 仅对明确的共享关闭取消重新排队，保持 Job、成功结果、请求历史和尝试预算；重启后恢复同一决定 |
| 中心部署/界面 | 当前仅分离的 8001/8002 和 API，无一体安装器 | 单地址路由、中心配置和状态展示；真实展示“关闭/停止中/可接单/离线” |

P2 不应通过调用节点内部 API、直接杀远程进程、读取 P1 数据库或推断“PAUSED 就一定可重试”来补缺。P1 交付实际停止机制及结构化原因后，P2 才能完成可靠迁移。

## 6. 新增验收 S01–S08

当前全部为 **NOT_RUN**，不替代原计划已验证或未验证的 L 系列用例。

| ID | 通过标准 |
|---|---|
| S01 默认关闭及中心选择 | 安装/启动/保存地址不注册共享；打开后只出现在所选中心；改中心前停止旧工作 |
| S02 55/45 接续 | 100 张真实不同输入，在第 56 张计算中关闭 A；55 个成功结果 SHA 保持，余下 45 张由 B 完成；无重复 Task 计数 |
| S03 真正停止 | 使用可观察的长识别确认按钮触发终止，不等整次推理自然结束；停止确认前不虚报空闲 |
| S04 竞态和迟到结果 | 成功先发布则保留；关闭先撤权则拒收；迁移成功不能被旧节点迟到结果覆盖 |
| S05 暂无替代资源 | 已成功结果可查，未完成项等待；B 上线并准备后自动接续原 Job |
| S06 重启和响应丢失 | 关闭请求/停止确认丢失及 P1/P2 重启后，同一撤出决定和执行映射恢复；不重复接单 |
| S07 保留现有取消 | 取消整个 Job 仍停止整批；原 DRAINING 仍完成已接工作；既有 3 次上限及未知结果对账不被破坏 |
| S08 再开启及准备中关闭 | 清理未结束不能接新任务；准备过程中关闭也真正停止；再次开启后核验并完成新的真实任务 |

S02 必须有两台实际设备与同一 Job 的关联证据。模拟测试可验证调度规则，但不能代替跨机和真实停止证明。
