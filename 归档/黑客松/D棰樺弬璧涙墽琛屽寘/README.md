# D 题执行计划：多设备任务平台

版本 **0.2.0**；修订日期 **2026-11-14**。这是根据团队最新分工重写的实施契约，取代 0.1.0 的商品图单一流水线和旧 P1/P2 职责。

**用户已确认：选择任务类型并提交文件，由 P2 按预设规则拆分和调度。P1 负责电脑联网、资源能力、模型准备和实际执行；P3 做页面；P4 做联调与验收。**

当前只有计划、机器可读契约和合成样例；应用、模拟服务、模型适配、基准工具和真实运行验收均待实现。通过接口 schema 只是 G0，真实连接和执行须继续通过 G1–G6。

| 人员 | 唯一主责 | 计划代码目录 | 第一份可独立交付物 |

| [P3](tasks/P3-前端体验.md) | 双服务前端与用户流程 | web | 用合成契约跑通选择类型、提交、预览、失败提示 |

四个编号是并行分工，不是四个串行阶段。P1 确认资源是否能接单；P2 决定任务如何拆、分给谁以及失败后是否再派。P1 不自动跨机重试，P2 不控制节点内部协议。

## 开工前共同冻结

1. 全体使用 contract_version=0.2.0，先读接口手册，再将自己的任务卡交给 AI。
2. P1/P2 在各自服务中暴露 health；P3 使用可配置的双服务代理；P4检查版本与角色权限。
3. P1 尽早发布已验证 profile。P2 可用模拟资源先开发，但真实 Job 创建要求 profile 已配置。
4. P4 发布共享样例和模拟状态用例；每人可以独立实现，不能各自发明另一组字段。
5. 先一份真实输入闭环，再两台物理设备，再故障恢复和正式数据。任何人不必等待其他人的全部功能完成才开始。

## 接口维护与修改规则

- HTTP 字段以 OpenAPI 为准；字段之外的运行语义以接口手册为准；任务数据与拆分规则以任务类型目录为准。三者冲突由提供方和调用方共同澄清，P4更新后再发布，不能各自选择解释。
- P1 对资源 API 行为负责，P2 对任务 API 行为负责；P4 是共享 contracts 的唯一落盘维护人，按双方确认的变更发布版本。任务类型变化必须同时得到 P1 执行器和 P2 拆分/合并负责人确认。
- 0.2.0 与旧版不兼容，不保留旧商品图字段作为隐式兜底。之后任何破坏字段/状态/计量方式的变更都升版本、更新样例和验收，并通知四人。
- 初始选定 OCR 图片和短 WAV 两种类型是本计划的工程范围，不代表模型已经可用，也不承诺支持任意任务。新增类型沿用相同资源/执行机制并注册新版本。
