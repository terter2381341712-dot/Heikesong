# 接口契约与联调手册

契约版本：**0.2.0**。这是四个人独立开发后连接的共同标准；当前服务和命令均待实现，不代表已有运行地址。

字段、类型、必填、枚举、HTTP码以 [OpenAPI](contracts/openapi.yaml) 为准；下面约定字段之外的顺序、原子性、状态和交接。完整 [合成样例](contracts/examples.json) 只用于开发；[类型目录](contracts/task-types.json) 定义首版能力。

## 1. 服务、路由、鉴权

| 提供方 | 配置 | 建议地址 | 路径前缀 |
|---|---|---|---|
| P1 | RESOURCE_BASE_URL | http://协调机局域网IP:8001 | /api/resource/v1 |
| P2 | TASK_BASE_URL | http://协调机局域网IP:8002 | /api/task/v1 |

BASE_URL 只包含协议、主机、端口，不含路径前缀，不带尾部 `/`。开发页面用代理转发两个前缀；生产同源反向代理。后端地址与浏览器代理地址可不同，由配置明确。禁止将 localhost 当成其他电脑可访问的地址。

实现时统一支持下列配置名，具体值由P1/P2交P4登记，不要求队友猜测启动参数：

| 配置名 | 使用方 | 约定 |
|---|---|---|
| RESOURCE_BIND_HOST / RESOURCE_PORT | P1 | 局域网演示默认0.0.0.0 / 8001，验证其他电脑可访问 |
| TASK_BIND_HOST / TASK_PORT | P2 | 默认0.0.0.0 / 8002，验证前端代理可访问 |
| RESOURCE_DATA_DIR / TASK_DATA_DIR | 各自服务 | 两个不同的本机绝对目录，不能指向同一个SQLite或混用测试数据 |
| RESOURCE_BASE_URL | P2、节点程序、P3代理、P4 | 对相应调用方实际可达的P1地址 |
| TASK_BASE_URL | P3代理、P4 | 实际可达的P2地址 |
| DEMO_TOKEN | P1、P2、P3用户输入、P4 | 两服务校验同一演示令牌 |
| TASK_TOKEN | P1、P2服务端、P4 | 调度权限，不进入前端构建 |
| JOIN_TOKEN | P1与节点程序 | 节点加入权限，与前两种令牌不同 |

所有含服务器占位地址的OpenAPI servers仅供开发替换，不能据此认为已有服务在线。

| 凭证 | 持有人 | 权限 |
|---|---|---|
| DEMO_TOKEN | P3、P4及演示用户 | P1资源/目录/文件/节点模式/事件，P2全部用户任务接口 |
| TASK_TOKEN | P2服务端、P4验收工具 | P1读取、文件上传、模型准备、执行与取消；不能放进浏览器 |
| JOIN_TOKEN / 节点会话凭证 | P1管理的节点程序 | 仅P1内部节点协议；不作为P2/P3依赖 |

公共接口统一 `Authorization: Bearer <token>`，两个 healthz 明确无鉴权。缺失/无效401，角色错误403。令牌从环境或安全输入读取，不进源码、日志、URL、ZIP。受控局域网演示，不新增复杂账号体系。

两种健康响应分别带 service=p1_resource/p2_task、contract_version=0.2.0、status=ok、server_time。P2健康不证明P1可达；查询目录/创建依赖请求若P1不可达，返回503 DEPENDENCY_UNAVAILABLE。

## 2. 公共数据规则

- JSON UTF-8，时间为带Z的UTC，耗时字段单位ms，字节bytes，内存bytes，利用率0–100。未知null，不用0代替未知。页面按北京时间展示。
- P2生成 job_id/task_id；客户端生成 upload_id/client_request_id/execution_id/preparation_id，使用UUID。P1生成worker_id、会话和artifact_id，调用方不得依赖ID内部编码。
- input_index从0开始，等于创建Job时数组顺序；结果完成顺序不能改变它。
- job_id属于业务批次，task_id属于逻辑输入，execution_id属于一次分派；三者不能混用。attempt_no从1开始，仅已接受执行计预算，最多3次。
- 请求正文不允许未声明字段。幂等载荷比较采用通过schema校验后的字段值：对象键顺序不影响相等，数组顺序影响相等；不把请求时间等本地信息混入重放载荷。
- 所有错误采用Error：code、message、retryable、request_id、details。不能HTTP 200配一个error字符串；正常业务对象中的FAILED状态与传输错误分别处理。
- code限定为OpenAPI枚举。details只使用声明的execution_id/preparation_id/artifact_id/job_id/retry_after_seconds/field，未知内部异常转INTERNAL_ERROR，不能把框架默认错误JSON当公共协议。
- 所有状态、artifact和幂等记录至少保留到该次演示/正式实验结束且人工归档，不在请求重试窗口自动删除。测试重置需停机并更换独立数据目录；新实验重新建立事件游标。

## 3. P1文件接口：先确保数据跨电脑能取到

`POST /api/resource/v1/artifacts` 为 multipart：upload_id（UUID）和file（二进制）。P1校验实际内容并保存**原始字节**，不统一改尺寸/重编码；OCR执行器内部预处理属于profile。返回Artifact元信息和download_path。

同upload_id、相同文件字节/文件名/内容类型：返回同artifact（首次201，重放200）；不同内容409 IDEMPOTENCY_CONFLICT。路径/目录片段从文件名剥离，不用文件名作为磁盘地址。

DEMO只能上传本版输入格式JPG/PNG/WAV；TASK还可以上传application/json结果或后续分片。JSON输出的注册不等于execution成功，只有P1节点执行协议可以提交执行终态。

元信息包括artifact_id、kind、original_name、content_type、sha256、size_bytes、media_info、download_path、created_at。图片宽高按EXIF方向纠正后的坐标空间报告，但存储的SHA仍是原文件字节。WAV报告时长、采样率、通道与编码；JSON的media_info相应字段为null。

`GET /artifacts/{id}` 取元信息；`GET /artifacts/{id}/content` 取二进制。download_path是以 `/api/resource/v1/artifacts/` 开头的相对HTTP路径，由调用方拼接P1地址，不是文件系统路径。内容和SHA必须一致。P1未确认写盘前不能返回成功。

类型不支持415，内容解码/参数不符422，文件/像素/数量超限413，权限401/403，不存在404。上传失败不留下可用于Job的半成品artifact。

## 4. 类型与模型准备：可安装、已缓存、已就绪要分开

P1 `GET /task-types` 返回类型的输入限制、参数语言、profile_id、profile_digest、configuration_state和result_schema。UNCONFIGURED时digest=null，P2不得创建真实Job；CONFIGURED只表示可按配置准备，不保证任何节点已READY。

P2 `GET /task-types` 返回“自己实现了拆分/汇总，且P1认识”的交集，保留未配置原因。P3从此处建立类型选择，不能只按本地写死菜单宣称已支持。

资源快照按每节点每profile报告：UNAVAILABLE（设备不兼容）、NOT_PREPARED、PREPARING、READY、ERROR；另报model_cached、实际backend/provider、模型SHA、自测、reason。未测试不能填verified=true。

按 [P1–P2 统一计划 1.0](../P1-P2统一修改与联调计划.md) 第3.4节补充选择语义：P2先匹配task_type/profile_id，再看状态。NOT_PREPARED且verified=false时，digest为null或等于Job冻结摘要均可请求准备，发出请求的digest始终取Job；非空错摘要等待配置对齐。PREPARING查询原准备或等待，不再开第二个准备；ERROR/UNAVAILABLE保留原因且不紧密重试。READY只在摘要严格匹配、verified=true、自测通过且实际backend/provider/model_sha256证据齐全时可执行；缺失或矛盾时明确等待。model_cached不能代替READY。补充合成样例见 [统一联调入口](../qa/p1-p2/README.md)，公共schema仍为0.2.0。

P2请求准备：preparation_id、worker_id、worker_session_id、task_type、profile_id、profile_digest。P1原子确认ONLINE+ACTIVE、空槽、配置匹配后返回202并异步准备，P2以同ID GET轮询。缓存命中仍需校验实际会话与后端；只有真实自测成功才能READY。

准备状态：ACCEPTED→DOWNLOADING→LOADING→VERIFYING→READY，可跳过无需执行的阶段；失败FAILED；业务拒绝REJECTED。progress未知为null，不能用计时器造进度。准备硬期限900秒，超时PREPARATION_TIMEOUT；首次下载、加载、自测各阶段记录。

准备和执行同用一槽。DRAINING后不接新准备，已有准备可完成再PAUSED。准备失败不算业务执行次数；P2不紧密循环重试同一失败准备，等待操作者修复或选择另一节点。重放同ID同请求返回原记录；同ID不同载荷409。通过schema的业务拒绝也持久记录，重复被拒ID始终拒绝。

## 5. P1单次执行接口：明确受理，再运行

P2 `POST /api/resource/v1/executions` 的必填字段：

| 字段 | 意义/约束 |
|---|---|
| execution_id | 本次分派唯一UUID，发请求前持久化；重传不换ID |
| job_id、task_id、attempt_no | 业务关联；attempt_no=1..3 |
| worker_id、worker_session_id | P2选定的设备与当前会话，防止旧快照误派 |
| task_type、profile_id、profile_digest | 冻结类型与执行配置，P1逐项核对 |
| input_artifact_id | P1可读取的输入文件标识 |
| parameters | 本版language=auto/zh/en，须在profile支持范围 |
| timeout_seconds | 10..600，首次接受开始计时，心跳不能延长硬期限 |

P1先检查幂等记录，再检查当前资源。已经成功的重传即使节点后来离线，也必须返回已存在记录，不能重新尝试接单。

对鉴权/schema通过的请求，P1用同一事务存请求指纹与接纳决定：

- 接受：201 Execution，状态ACCEPTED，原子占槽；同ID重放200，返回该执行的**当前快照**。
- 业务拒绝：409 Error，details.execution_id为同请求ID，且GET该ID可得到REJECTED记录。RESOURCE_BUSY、NODE_UNAVAILABLE、SESSION_CHANGED、CAPABILITY_NOT_READY、PROFILE_MISMATCH等明确区分。重放同ID仍返回409及原拒绝，不能后来重新接受。
- 同ID不同载荷：409 IDEMPOTENCY_CONFLICT，不覆盖旧记录。鉴权/schema错误401/403/422不创建执行记录。

执行申请中目标/输入引用不存在、输入与类型不符等业务检查同样以409 REJECTED持久记录（NOT_FOUND/INPUT_INVALID等），不能与GET不存在的404混为一谈。retryable=true的资源拒绝允许等待后新ID申请；PROFILE_MISMATCH、INPUT_INVALID、UNSUPPORTED_TASK_TYPE、PARAMETER_UNSUPPORTED等retryable=false拒绝令该Task FAILED，不消耗接受次数，也不自动改profile。P2可提示用户修复配置后新建Job。

有效空槽条件：节点ONLINE、ACTIVE、cleanup_pending=false、没有当前执行/准备，max_slots=1、reserved_slots=0、available_slots=1；模型未READY不阻止准备使用空槽。准备/执行请求都须匹配当前会话；所需能力READY、验证通过且profile/digest匹配是**执行接纳的附加条件**。准备和执行共用一槽，活动工作、非ACTIVE、离线或待清理时available_slots=0。资源查询只是快照，不承诺将来一定接单。

P1接受后由节点程序实际领取并运行。内部工作协议归P1，P2只观察Execution。租约15秒，节点每3秒心跳续租，但不能越过hard_deadline_at。首次接受15秒内未被有效领取/续租也会过期。节点输入传输、执行和结果回传在同一次硬期限内；准备模型在接受前完成。

Execution带原请求、状态、输入SHA、created/accepted/started/finished时间、租约与硬截止、结果artifact、timings和error。worker timings测下载/读取输入、推理、后处理、本地写结果及total_worker_ms；total_worker_ms不含结果上传。端到端窗口使用P1服务器accepted_at至finished_at，包含分发/传输/协调成本，不用不同机器墙钟相减。

P1先将输出写入execution专属临时文件，检查结果schema、输入关联、profile与当前提交权，完成文件持久化后再原子发布artifact引用和SUCCEEDED。任何可查询的SUCCEEDED必须已有完整可下载结果；无数据库引用的临时文件不对外显示。晚到提交或重复提交不同内容不得覆盖已有文件。

## 6. 不确定请求、重试与去重

这是连接验收必须覆盖的场景：

1. P2在本地事务保存待发送请求，再发P1；同一Task最多一条未对账分派。
2. P2超时/断网/5xx：结果未知，保持DISPATCHING或原状态。用同ID同载荷重放，或GET对账。**一次GET 404不证明原POST不会晚到，不能据此新开另一单。**
3. P1恢复后重放可得到确定受理/拒绝；P1把业务拒绝也持久化，因此确定REJECTED后，晚到原请求不会再接受。
4. 确定REJECTED后，P2可用新execution_id重新申请，attempt_no不增加；至少1秒退避，单节点不超过每秒一次拒绝重试，先刷新资源。
5. 确定已接受后才增加attempts_used。其FAILED且retryable=true才能开启下一attempt_no；最多3次已接受尝试。P1不替P2重派。
6. 单次成功提交、整个执行受理、Job创建、上传四层分别幂等。逻辑Task只接受一个最终结果；故障可有重复物理计算，其成本保留，不能宣称计算恰好执行一次。

P2不对已接受执行另设本地“猜测失败”的定时器。P1不可达时等待并显示依赖故障；P1重启须给所有旧活动执行明确失败结果，P2收到后才能按预算重试。

P2建议每1秒一轮查询资源/准备/执行，单请求未返回不叠加同类轮询；网络失败采用1、2、4、8秒退避，最大10秒。JSON请求默认连接超时2秒、响应超时10秒，文件传输可单独设60秒；这些客户端等待上限不能作为execution失败判据。准备与执行POST应快速返回受理记录，不阻塞至模型工作完成。

## 7. 取消、节点退出与重启

P1 cancel是幂等操作。已终态返回原执行200；活动执行返回CANCEL_REQUESTED（202），撤销结果提交权并通知节点停止，停止确认后CANCELLED。成功与取消在P1事务中决定先后，成功先提交则保留成功，取消先撤权则拒收之后的结果。节点失联时可确定CANCELLED并撤销会话；该设备直到停止旧计算、重建会话前不可重新接单。

执行超时或节点失联可将执行标FAILED，但cleanup_pending未清除或节点OFFLINE期间available_slots=0。防止“服务器释放逻辑记录，但设备旧计算仍在跑”导致实际并发失控。节点主进程独立心跳，推荐使用可终止子进程执行模型。

P1 mode接口接受ACTIVE/DRAINING。DRAINING禁止新准备/执行，当前工作完成后PAUSED；不强杀当前模型。ACTIVE恢复后仍需满足ONLINE、配置与能力要求。

P2取消Job：持久cancel_requested=true，停止新分派；未派发Task直接CANCELLED，已知execution请求P1取消；未知接单先对账，必要时重放原申请再取消，不能新开尝试。Job只在所有Task确定终态后CANCELLED。已成功项保留在results与ZIP；已终态Job取消返回原状态，不修改既有结果。

P1重启保留文件、终态和幂等记录；未终态执行FAILED/RESOURCE_SERVICE_RESTARTED（可重试），准备FAILED，旧会话失效。P2重启恢复请求ID和映射，先查询或重放再继续，不能用重新建任务代替恢复。

## 8. P2 Job与结果接口

创建必填client_request_id、task_type、profile_id、profile_digest、input_artifact_ids、parameters。P2从P1查询元信息并校验配置、语言、格式、限制和重复SHA；输入数组1–200项、一个Job一种类型。P1不可达503 DEPENDENCY_UNAVAILABLE，profile未配置503 PROFILE_UNCONFIGURED，未知/不匹配输入422，幂等冲突409。

首次创建201 Job；同请求同载荷重放200返回当前Job。P2必须先持久化Job、Task与顺序再回应。profile已配置但没有设备READY时可接受Job并WAITING_FOR_RESOURCES。

每个文件一个Task，input_index从0连续。Task包含输入元信息、状态、attempts_used、当前execution、所有分派摘要、结果artifact和等待/错误原因。REJECTED分派可多条，但已接受尝试≤3；同Task不能同时存在两条未终止且未撤销的执行。

Job状态优先规则：已终态保持不变；取消标记且仍有非终态→CANCELLING；取消标记且全终态→CANCELLED；全成功→SUCCEEDED；全FAILED→FAILED；全部终态且有成功有失败→PARTIAL_FAILED；有RUNNING/DISPATCHING→RUNNING；有等待且无人运行→WAITING_FOR_RESOURCES；其余QUEUED。counts按Task唯一ID统计且各分状态之和=total。

GET results允许中途读取，每个输入都有一项；未完成的result=null，失败保留error。P2获取P1结果文件后检查schema、task_type、input_artifact_id再汇总。combined_text按input_index将成功项text用两个换行连接；失败在items中保留，不假造文本占位为成功。

P2必须把校验后的结果JSON持久保存后，才原子地将Task置SUCCEEDED；results/ZIP使用这份持久结果，完成后的下载不依赖P1再次在线。P1已执行成功但结果尚未取回时，Task保持RUNNING并注明“结果待取回”，保留同一execution继续读取，不为网络故障重新推理。

OCRResult：schema_version=1.0、task_type=ocr.image.v1、input_artifact_id、image_width/height、text、blocks。bbox=[x0,y0,x1,y1]，相对EXIF方向纠正后的原图像素坐标，0≤x0≤x1≤width、0≤y0≤y1≤height；缩放推理须映回原图。confidence未知null。无文字可text=""/blocks=[]，其业务正确性由参考判定。

ASRResult：schema_version=1.0、task_type=asr.file.v1、input_artifact_id、duration_ms、language或null、text、segments。每段0≤start_ms<end_ms≤duration_ms，按时间排序且不重叠；静音可空文本/空segments。不同文件的时间戳各自从0开始。

GET download只在SUCCEEDED/PARTIAL_FAILED/FAILED/CANCELLED可用，未结束409 JOB_NOT_TERMINAL。ZIP固定包含manifest.json（Job/输入/状态/执行/失败原因）、results.json（JobResults）、combined.txt、每个成功Task一个results/{input_index四位}-{task_id}.json。不得包含令牌、租约、服务器绝对路径或参考答案。

## 9. 边界错误表

| 情形 | HTTP/状态 | 调用方动作 |
|---|---|---|
| 没/错令牌、角色错误 | 401 / 403 | 修配置，不重复业务提交 |
| 请求schema错误 | 422 INVALID_REQUEST | 修请求，编辑后换幂等ID |
| 类型、语言、输入不符 | 422 INPUT_INVALID / UNSUPPORTED_TASK_TYPE / PARAMETER_UNSUPPORTED | 显示原因，不自动换类型 |
| 文件超限、不支持格式 | 413 INPUT_TOO_LARGE / 415 UNSUPPORTED_MEDIA_TYPE | 修改输入 |
| 同幂等ID不同载荷 | 409 IDEMPOTENCY_CONFLICT | 保留原任务，明确操作冲突 |
| 节点忙、离线、会话变化、能力未就绪 | 409 + REJECTED记录 | 确定拒绝后刷新资源/等待/换新execution_id |
| profile摘要变化 | 409 PROFILE_MISMATCH + REJECTED，retryable=false | 该Task失败，保留Job原摘要；提示修复后新建Job |
| 已接受执行失联/租约/硬超时 | Execution FAILED + retryable=true | P2按最多3次预算重新调度 |
| 已接受执行输入/结果无效 | Execution FAILED + retryable=false | 终止该Task，其他Task继续 |
| Job未结束下载 | 409 JOB_NOT_TERMINAL | 等终态 |
| 中心依赖不可达 | 503 DEPENDENCY_UNAVAILABLE | 保留ID与状态，对账后继续 |
| profile未配置 | 503 PROFILE_UNCONFIGURED | 不声称可用，等待P1发布 |

P1内部节点晚到提交用STALE_EXECUTION，返回409并记录事件；P2/P3不调用该内部提交接口。POST响应丢失不能等同上述“明确拒绝”。

## 10. 最小真实连接步骤

以下为**实现后**的验收顺序；本包没有运行服务或已有效令牌。

1. 两服务health均为0.2.0。P4用DEMO查询P1资源、用TASK读取目录；用DEMO下发execution应403。
2. P3/P4向P1上传一个新文件，另一台电脑下载并核对SHA。
3. P1发布一个真实CONFIGURED profile，兼容新节点以NOT_PREPARED/null上线。
4. P3或等价HTTP验收客户端向P2创建Job；P2冻结profile，自动持久化并发出preparation，真实READY后才落库并发出execution。验收客户端不能手工准备绕过此路径；保存Job/Task/preparation/execution/worker/session/input关联。
5. P1完成并存结果；P2核对、汇总；P3读取results和ZIP。输入、结果和节点均能追溯。
6. 重放上传、Job、execution请求，结果数量不增加；修改同ID载荷应409。
7. 扩展到两台物理设备和多份输入；再执行故障与取消矩阵。不能跳过最小闭环直接用UI在线图标验收。

## 11. P1→P4离线基线契约

此命令是**P1待实现的交付要求**，不是已可运行脚本：

```text
python -m node_agent.benchmark --manifest <inputs.jsonl> --profile <profile.lock.json> --backend cpu --threads 2 --output-dir <目录> --run-id <本轮ID>
```

manifest每行是BaselineInput：input_index、input_artifact_id、local_path（本机可读绝对路径）、input_sha256。它是离线工具输入，不作为跨电脑HTTP文件地址。文件SHA须匹配；profile决定类型与执行器。P4可先上传固定输入再下载到每台，复用artifact ID及原字节。

--profile读取符合RuntimeProfile的单个JSON锁文件，文件内不放自身profile_digest。基线程序对原始锁文件字节计算SHA，与线上目录digest核对；它不同于包含多个未验证草稿的runtime-manifest.example.json。

同一执行器负责读取、预处理、推理、后处理、写规范JSON；stdout只输出UTF-8 JSONL，日志到stderr。每个输入一条BaselineRecord，最后一条BaselineSummary；字段以OpenAPI components中的同名schema为准，样例已提供。

BaselineRecord含run_id、worker_id、类型/profile、input_index/ID/hash、实际backend、开始/结束UTC、单调耗时、SUCCEEDED/FAILED、结果本机路径及SHA、error。输出规范JSON里的input_artifact_id与manifest一致。

BaselineSummary含实际测量窗口起止、wall_ms、单列warmup_ms、总数/成功/失败。先预热再开始整批窗口，窗口含读取/计算/后处理/写文件和循环开销；不能只累加模型内核时间。结束摘要写出后退出：0=全部执行结构成功，1=至少一输入失败，2=配置/manifest/启动失败。质量是否合格由P4另判，不由exit 0推断。

## 12. 提供方与调用方各自验收

提供方负责准确schema、错误/状态、幂等持久化、字节与资源事实；调用方负责权限、顺序、稳定ID、未知状态对账和明确错误处理。P4的共享模拟服务应按同一规则覆盖正常、忙碌、准备、失败、取消与延迟；模拟程序仍待实现。

四人交付最小可运行模块时，附版本、地址/端口、环境变量、启动停止命令、独立数据目录、一次可复现请求与响应。具体用例见 [44项验收矩阵](03-验收与压测.md)。只有对应真实用例通过，才能说“已经连接起来”。

本轮依统一计划澄清恢复责任：X01（P1重启）由P1主责，X02（P2重启）由P2主责，双方配合对账。本轮P2汇总共享资料与L01–L19记录，P4参与时独立复验；P2协议测试通过不改变尚未执行的真实联合用例状态。
