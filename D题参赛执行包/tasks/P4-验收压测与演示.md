# P4：契约检查、联调验收、性能证据与演示

版本：0.2.0。从开工起验证模块可连接；不替 P1/P2/P3 实现产品模块。

## 1. 职责与目录

计划负责 `qa/`、`bench/`、`demo/`、`scripts/`、根 README、统一发布的 `contracts/`。P1 定义资源接口行为，P2 定义任务接口行为；你汇总双方确认的变更并发布版本，不单方面改行为或降低标准。

问题给最小复现，由原模块负责人修复，你回归；不直接修改资源服务、节点、任务服务、拆分器或前端来掩盖失败。

## 2. 开工交付

1. 按 [验收矩阵](../03-验收与压测.md) 建结果清单，全部 NOT_RUN；记录版本、设备、命令、时间、原始证据和 PASS/FAIL。
2. 检查 [OpenAPI](../contracts/openapi.yaml)、[样例](../contracts/examples.json)、[任务类型](../contracts/task-types.json)。结构通过与运行互通通过分开。
3. 为 P2 提供模拟 P1，为 P3 提供模拟 P1+P2，覆盖等待/拒绝/失败/取消，不只返回固定 200。模拟工具待实现，本包没有附带可运行服务。
4. 准备授权图片、短 WAV、参考文本和困难样本。参考答案放验收环境，不放运行服务输入/模型目录。
5. 组织 P1 验证真实设备互通，记录网络、端口、配置和实际后端；联网实现仍属 P1。

## 3. 连接门槛

| 门槛 | 必须验证 | 修复责任 |
|---|---|---|
| G0 契约一致 | 同版本、样例过 schema、状态含义一致 | 提供方提出修订，P4发布 |
| G1 基础互通 | health、鉴权；跨电脑上传/下载字节一致 | P1/P2 服务，P3代理 |
| G2 一次执行 | 一台真实设备执行；同 ID 不重复计算 | P1 |
| G3 用户闭环 | P3→P1上传→P2 Job→P1执行→结果/ZIP | 各自模块 |
| G4 真实协同 | 同类同 Job 至少两台物理设备各贡献有效结果 | P1/P2 |
| G5 边界行为 | 竞争、丢响应、掉线、取消、重启、旧结果、部分失败 | 按 R/T/U 用例归属 |
| G6 正式证据 | 固定口径质量、单机/多机、采样和演示 | P4汇总，P1/P2提供入口 |

局部模拟通过不能替代 G3–G6。

## 4. 所需输入与交接

- P1：平台启动方式、profile 锁定文件、实际能力、资源/执行/事件、离线基线入口。单机入口属于 P1，不在你这里另写一套推理。
- P2：任务接口、拆分/汇总规则、Job/Task/execution 关系、重启恢复行为。
- P3：可配置真实页面、错误与等待提示。
- 各模块：独立数据目录、健康检查、停止/重启说明。测试清理由停机后的独立目录完成，不新增任意改数据库接口。

离线基线的输入及 JSONL 格式见 [接口手册](../05-接口契约与联调手册.md)，这是 P1 与你之间的依赖契约。

## 5. 正式质量和性能

OCR、ASR 分开验质量和计量，不将图片数与录音时长相加。先每设备本地完整执行器，再经 P1 单节点、经 P2 完整单节点，最后同类型多节点。主聚合效率分母用本地完整执行器，其他路径对照单列。

至少两台独立物理设备；冻结设备集合、输入、profile、后端、线程/槽位/批大小、窗口。动态节点实验单列。交付配置、输入清单、逐任务/执行 CSV、采样 CSV、汇总 CSV、事件 JSONL、质量与性能报告；保留失败和重复耗时，未知指标 null/N/A。

## 6. 演示与最终交付

演示选择类型并提交新文件、两机完成、结果下载、节点变化。用户与商业采用尚是假设，有反馈才写成事实；设备授权、模型/数据来源许可、成本估计、AI/第三方说明进入材料。

由未写对应模块的人按说明重启并操作；源码、依赖、契约、样例、报告和日志对应同版本，检查提交回执。工作截止暂沿用 2026-11-15 12:00 北京时间，须核对主办方通知。

## 7. 缺陷与验收记录

每条含用例 ID、契约/代码版本、设备、最小步骤、预期/实际、请求响应或日志、复现次数、负责人及回归结果。核心失败写 FAIL，未执行写 NOT_RUN。

提供方保证 schema 和运行语义；调用方保证调用顺序、权限、幂等 ID 与错误处理；P4验证两端连接，不以“字段能解析”代替业务正确。
