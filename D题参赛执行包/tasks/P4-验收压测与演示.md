# P4：联调验收、性能证据与产品演示

你的职责是让“做出来”变成“能验证、能讲明白、能交付”。你是当天项目推进人，不是最后才开始写 PPT 的角色。

## 给 AI 的任务说明

> 为 D 题“弹性商品图工坊”实现黑盒验收、性能测试和交付材料。先读取接口、验收文档和时间表。只编辑 `qa/`、`bench/`、`demo/`、`scripts/` 和项目根 README；不要直接修改 server/worker/web。优先建立真实素材清单和 smoke 脚本，随后测试两机、动态增减、重复提交与旧租约。可以用模拟 Worker 检验协议，但必须清楚区分模拟测试与真实物理设备证据。按固定输入和正确性口径生成 CSV/JSONL/Markdown 报告，不填任何未经测量的性能数字。发现 bug 给出最小复现并交给对应负责人。

## 开工就做

- 建 `qa/results.md`，登记 A01–A20 和负责人，状态先全部 NOT_RUN。
- 用四人共同接受的契约制作 smoke 工具；P1 API 未齐时先写请求与断言，记录未通过，不能伪造 PASS。
- 准备获授权的新照片、质量样本、困难样本和评委临时输入入口。
- 验证三台电脑能访问协调机；记录防火墙、热点/局域网方式，不通过关闭全部安全设置省事。
- 找 1–2 位相近用户了解批量处理需求；找不到就把商业部分写成明确假设。

## 测试实现边界

- 测试租约和竞争可以使用受控时间及模拟 Worker；不要把这些当真实算力证据。
- 正式性能必须采集至少两台独立物理机器；全部参与计算的设备都登记。
- 先运行各设备本地独立完整流水线，作为主效率指标分母；再做同服务路径的单 Worker 对照，分离网络/协调开销，最后跑多 Worker。不混用两种单机基线。
- 测试工具能导出 task/attempt/设备/输入 hash/耗时/质量核验，不能只保存最终平均数。
- 增减节点的时段单独报告；不与固定节点吞吐混算。
- fixture 数据只在开发模式存在，提交前检查页面不在 MOCK 模式。

## 缺陷反馈格式

每条包括：验收 ID、代码版本、设备集合、最小操作、预期、实际、请求/响应或日志、复现次数。P1/P2/P3各自修自己的目录；P4 回归。接口变更由 P1统一写契约。

## 最终验收权

核心用例未通过就明确列 FAIL；以团队共同看到的真实行为为准。最后一遍由未写对应模块的人照 README操作。负责检查提交时间和回执，预留 11:00–12:00 上传与现场准备时间。
