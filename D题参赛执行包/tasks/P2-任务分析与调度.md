# P2：任务分析、拆分、调度与汇总

版本：0.2.0。用户选择任务类型并提供文件，P2 按预设规则处理，不要求自然语言意图识别。

## 1. 交付边界

你拥有用户 Job、逻辑子任务、调度决策和最终结果，通过 P1 的资源与执行接口使用电脑。

| 你负责 | 对方负责 |
|---|---|
| 类型/输入/参数校验，创建 Job | P1 文件保存和跨机传输 |
| 按类型拆分、编号、保存输入顺序 | P1 执行一个已拆好的子任务 |
| 选择 worker_id/profile、申请执行 | P1 原子确认能否接单并占槽 |
| 请求模型准备、等待就绪 | P1 下载、校验、加载、自测 |
| 业务重试、去重、恢复、取消 Job | P1 单次执行终态、拒收旧结果 |
| 汇总、最终 JSON/TXT/ZIP | P3 页面，P4 独立验收 |

计划代码归属：`task_service/`、`splitters/`、`aggregators/`、`tests/tasks/`。不实现 Worker、硬件探测或模型推理。

## 2. 输入与依赖

读取 [架构](../02-架构与接口说明.md)、[接口手册](../05-接口契约与联调手册.md)、[OpenAPI](../contracts/openapi.yaml)、[类型目录](../contracts/task-types.json)、[样例](../contracts/examples.json)、[验收表](../03-验收与压测.md)。

需要 P1 的 RESOURCE_BASE_URL、TASK_TOKEN。P1 暂未就绪时使用 P4 按契约提供的模拟 P1，模拟数据不能用作性能证明。

## 3. 对外接口

TASK_BASE_URL 默认建议端口 8002；共同前缀 `/api/task/v1`。

| 接口 | 调用者 | 保证 |
|---|---|---|
| `GET /healthz` | 所有人 | service=p2_task、contract_version=0.2.0；不假称 P1 已在线 |
| `GET /task-types` | P3/P4 | 你有拆分规则且 P1 认识的类型，含配置状态 |
| `POST /jobs` | P3/P4 | client_request_id 幂等；校验类型/profile/文件；后台处理 |
| `GET /jobs/{id}` | P3/P4 | Job/Task ID、顺序、计数和 execution 引用稳定 |
| `POST /jobs/{id}/cancel` | P3/P4 | 停止新分派，撤销未完成执行，保留已有成功 |
| `GET /jobs/{id}/results` | P3/P4 | 可读部分结果；保留顺序和失败项 |
| `GET /jobs/{id}/download` | P3/P4 | 终态 ZIP；未结束 409；失败/取消也提供清单 |

你只通过 P1 的公开 HTTP 接口访问资源、文件、准备与执行，不读其数据库，不直连 Worker。

## 4. 首版拆分与合并

- ocr.image.v1：一张 JPG/PNG 一个子任务；v1 不拆单图、不接 PDF，按 input_index 汇总。
- asr.file.v1：一个符合约定的短 WAV 一个子任务；v1 不自动切长音频，不同录音时间戳各从 0 开始。
- 一个 Job 一种类型、1–200 个不同内容的输入；同 Job 重复内容 SHA 拒绝。不同类型分别建 Job。
- PDF/长音频后续新增版本化规则，同时定义执行输入、边界/时间戳合并和验收。

选择 P1 发布的 profile 并保存 digest；不在一次 Job 中自动换模型或修改参数。

## 5. 调度与重试

1. 创建前查询真实类型配置和输入元信息；未配置返回 503 PROFILE_UNCONFIGURED。已配置但没设备时可建 WAITING_FOR_RESOURCES Job。
2. 选择同类型/profile READY、ACTIVE、有空槽的节点；兼容但未准备时调用 preparations，等 READY。准备不算执行尝试。
3. 无资源保留任务并说明原因；首版可按 worker_id 稳定轮询空闲节点，不按内存比例硬分整批。
4. 先落库 task_id、attempt_no、execution_id、完整请求，再 POST。断网/超时/5xx 属于结果未知：查询或重发原 ID 原载荷，不换节点再派；一次 404 不能证明原请求不会晚到。
5. 只有 P1 明确记录 REJECTED，才可等待后换 execution_id 重新申请，拒绝不增加 attempts_used。同任务只允许一笔未对账分派。
6. 已接受执行才算一次尝试。FAILED 且 retryable=true 才增加 attempt_no 重派，最多 3 次。输入错误、输出无效、profile 不匹配等直接终止。
7. P1 管理已接受执行的期限；你不因自己的 HTTP 超时判断它失败。P1 整体断开时暂停新派发并显示连接问题，恢复先对账。
8. 对成功结果核对 schema、task_type、input_artifact_id，持久保存JSON后再置Task成功；results/ZIP读取本地持久结果。P1结果尚未取回时保留RUNNING和同一execution继续读取，不重新推理。不让迟到旧尝试替换最终结果。
9. 重启后恢复持久任务，先查询/重放原 execution，再继续派发，不能新建一批重复执行。

## 6. 交接产出

给 P3：TASK_BASE_URL、演示令牌配置、完整生命周期和成功/等待/失败/取消样例。浏览器离开不取消 Job。

给 P4：启动与独立数据目录说明、拆分/合并规则、输入 hash、Job/Task/execution 关系、尝试和失败证据。OCR/ASR 分开计量；你的 succeeded 不代表人工质量已合格。

## 7. 独立自测与完成定义

用模拟 P1 测无节点、模型准备、忙碌拒绝、响应丢失、失败重派、乱序完成、重复响应、部分失败、取消、重启对账。证明请求幂等、顺序稳定、最多三次接受尝试、未知结果不重复派单。

真实联调从一台设备、一种已配置类型、一份新输入开始，再接两台物理设备。主责 T01–T10，参与 I01–I08，标准见统一验收表。

别人只按契约即可提交、查询、取消、取结果，且能由原始执行记录复核真实跨机行为，才算完成。

## 8. 给开发 AI

只实现任务平台，不写 Worker、执行器或网页。所有能力来自 P1 契约。接口不通先查版本、路径、鉴权、样例；修改字段或语义先交 P4 汇总并取得提供方/调用方确认，不临时读取其他模块数据库。
